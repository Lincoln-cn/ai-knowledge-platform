# 恢复演练记录（`#75` 判据 ③）

> 这份文件是**记录格式**，不是演练结果。填满它并让 `python scripts/restore_drill.py check` 退 0，
> 才叫"演练过"。任何一个键没填、或 RPO/RTO 超出 `deploy/README.md` 第七节的数字，检查器都会红。

**为什么要有这份记录**：`deploy/README.md` 写着 RPO ≤15 分钟、RTO ≤4 小时，但"没演练过的备份不算备份" ——
没有记录，那两句话只是意向。演练频率建议每季度一次，以及在**换存储介质、换 PG 大版本、变更备份脚本**之后各补一次。

## 一、怎么跑（演练执行人照着做）

1. 准备一台**不承载线上流量**的机器与一个空库（不要在原库上恢复）；
2. 取一份**指定时点**的备份：每日全量 `pg_dump -Fc` + 该时点之前的 WAL 归档；
3. 记下 `恢复开始`（开始执行 `pg_restore` 的时间），恢复到目标时点；
4. `恢复结束` = 抽样验证通过的时刻；
5. 抽样验证至少覆盖：① 行数核对（`kb_document` / `kb_segment` / `cv_message` 与备份时点对比）；
   ② 一条真实检索（用"抽样 10 条问题"复现原先命中的文档）；③ 一条登录；
6. 把数字填进下面的模板，跑检查器。

## 二、记录模板（把「待补」逐项替换）

- 演练日期：待补
- 备份来源：待补（哪一份备份、在哪台介质、谁取的）
- 目标时点：待补（ISO-8601，UTC）
- 恢复开始：待补
- 恢复结束：待补
- RPO：待补（**实际**丢失了多少分钟的数据 —— 不是承诺值）
- RTO：待补（恢复开始到抽样验证通过，实际用了多少分钟）
- 行数核对：待补（三张表的差异，以及差异的**原因**）
- 结论：待补（只写「通过」或「失败」+ 一句依据）

## 三、检查器

```bash
python scripts/restore_drill.py check deploy/restore-drill-record.md
python scripts/restore_drill.py --self-check   # 离线自检，已进快闸
```

★ 检查器不判断"抽样验证做得对不对"，它只判断**这份记录是否完整、数字是否在限内**。
把不完整的记录判成合规，比没有记录更糟 —— 所以模板里留「待补」是刻意的：没填完一定红。
