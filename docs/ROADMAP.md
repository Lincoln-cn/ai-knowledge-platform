从当前状态到「可用阶段」的完整路径。**这份是唯一的可执行计划** —— 设计理由看
[`系统设计方案/04-MVP最小验证系统设计.md`](系统设计方案/04-MVP最小验证系统设计.md)，

## 一、这份计划的形状

三条轨并行，一条编号：

| 轨 | 内容 | 谁主导 |
|---|---|---|
| **后端主线** | 里程碑 M0 → M6 | 后端 |

**顺序是：前端先行到可用 → 按那份清单做后端接口。**

## 二、「可用阶段」的定义

**这是转公开（private → public）的门槛。** 三张清单全绿才算到。

### 2.1 功能清单（端到端场景全部走通）

`04` §三 定义的三个场景，在 `VITE_USE_MOCK=false` 下无阻塞完成：

| 场景 | 内容 | 验证的假设 |
|---|---|---|
| **S1** | 知识运营：建库 → 上传真实文档 → 切分 + 调参 → 向量化（真实进度）→ 命中测试 → 停用分段后不再命中 | H1、H3 |
| **S2** | 应用配置：建应用 → 选模型 → 写提示词 → 绑知识库 → 发布 → 生成公开链接 → 外部访客未登录提问得带引用答案 → 撤销后 1 分钟内失效 | H3、免登录安全 |
| **S3** | 终端用户：流式作答 → 引用可展开溯源 → 连续追问 5 轮 → 生成中停止保留已生成内容 → 重新生成 → 赞/取消赞刷新后仍在 → 会话评分 | 交互完整性 |

### 2.2 数据真实性清单（`04` §6.2 的 A1–A9）

**A2 是最容易被绕过、也最能说明问题的一条**：任意时刻的进度与状态必须与数据库实际状态一致，
**刷新页面不重置**。前端现在的进度是 mock 推进的 —— 这一条通过，就等于"后端真的接管了状态"。

A1 全链路 · A2 状态真实性 · A3 失败可见（人为构造失败，界面给出可读原因与重试）·
A4 引用可溯源 · A5 停止与重生成 · A6 多轮上下文（10 轮仍能指代第 1 轮实体）·
A7 权限生效（前端看不到按钮 **且** 直接调接口被拒）· A8 免登录安全 · A9 模块边界校验通过。

### 2.3 质量与工程清单

| 项 | 门槛 |
|---|---|
| 量化指标（`04` §6.3） | **B1 命中率 ≥70%** · **B2 答案可用率 ≥75%** · B3 引用准确率 ≥80% · **B4 首字延迟 ≤10s**（CPU/4B）· B5 完整回答 ≤60s · B6 入库 ≥3 段/秒 · B7 连续 200 次问答无未处理异常 |
| 前端闸门 | `vue-tsc` 0 · 模板配平 · 设计系统维度全 0 · `build:mock` ✓ · 11 个脚本 exit 0 · console 0 |
| 后端闸门 | 架构校验测试通过 · 关键链路集成测试通过 · **契约漂移检测**通过（见 §七） |
| 工程 | **CI（GitHub Actions）跑通**：前端 11 个脚本 + `vue-tsc`/`build` + 后端四类闸门 · `docker-compose.yml` 一条命令起（应用 + PG/pgvector + 模型网关）· 示例数据种子 |
| 文档 | 面向贡献者的「如何加一个模块」· CHANGELOG 起点 |

> **B1/B2 不达标不是"功能没做完"，而是假设 H1 不成立** —— 此时正确的动作是回机制二（检索策略）
> 与问答对（P2 升 P0）做优化，**不是继续加功能**。这条判断规则写在计划里，是为了在指标不达标时
> 有据可依地不乱改方向。
>
> ★ **这三张清单是 MVP 的唯一定义（范围不加码）** —— 企业级缺口（工具调用与审计 / MCP / 多租户 / 国密 / 备份演练 / 技能市场等）
> **一项都不进这三张清单**：它们要么「**留缝**」（进第 16–18 周但不占功能位）、要么「**只记账**」（Issue 开着、代码不动）。

### 3.5 ★ 权限模型缺了一层：只有「操作」，没有「范围」

**这是本轮发现的、影响面最大的一处设计缺口。** 详细设计见
[`系统设计方案/07-角色与数据权限模型.md`](系统设计方案/07-角色与数据权限模型.md)，此处只记差距。

| # | 事实 | 读数 |
|---|---|---|
| 1 | 权限点 **13 个，全是"操作"** | `knowledge:view` 是**无参数**的 —— 能回答「能不能看知识库」，**回答不了「能看哪些」** |
| 2 | 契约里**归属/可见性字段 0 个** | `owner` / `visibility` / `sharedWith` / `orgId` 全无 |
| 3 | `Role` 类型**没有数据范围的表达位** | 只有 `permissions: string[]` |
| 4 | **旧系统是三层权限**（菜单 + **数据** + 接口，`FR-01-05`） | 新系统只有菜单（路由 meta）+ 接口（权限点）⇒ **数据层丢了** |
| 5 | ⇒ **普通用户看到的是「整个工地，只是按钮少几个」** | `USER` 只有 **2 个权限点**，却看到 **4 个模块**，其中 `知识库` 与 `应用管理` 是**全平台建设面** |

**为什么不能靠加权限点解决**：那是**集合关系**（自己的／被共享的／全平台的），
不是**动作** —— `knowledge:view` 加多少前缀都表达不了。

**处置（已写进 07）**：引入 `ownerId` + `visibility` + `sharedWith`（资源侧）与
`dataScope: own | shared | all`（角色侧），可见性判定**只在后端一处实现**；
并把「普通用户」拆成 **使用者**（纯消费）与 **个人建设者**（能建自己的）两个角色。
`04` 里「MVP 采用全员可见」那条口径**已作废**。

**四件待拍板**（07 §七）：管理员能否看别人的会话 · `CREATOR` 能否建编排应用 ·
`public` 可见性是否进 MVP · 新建资源的默认可见性。**建议四条全选"默认收窄"** ——
数据权限放开容易、收回难。

## 四、里程碑总表
**规模**：后端 2 人 + 前端 1 人 +（兼）测试 1 人（`04:302`）。人力不同按比例缩放。

**覆盖度对账**：前端契约共 **98 个端点**（12 个域 + `POST /auth/refresh`），下表把它们**全部**落到里程碑上。

|---|---|---|---|

但它的 §七 里程碑表没有给这一块落位。这是一处真实的范围漏算，不是估算变松。

### 4.1 每个里程碑的验收怎么量

| 里程碑 | 验收口径（可复核） |
|---|---|

| **M1** | 登录成功 + 令牌刷新（401 静默重试一次）+ 权限点下发；注册并加载一个模型 ⇒ 状态从「加载中」变「已加载」（**加载态存服务端**，刷新页面仍在） |

| **M5** | 赞/取消赞互斥可撤销且**刷新后仍在**；「已处理」必须填处理说明；满意度无数据时为 `null` 而非 `0` |
| **M5.5** | 能画出流程并存草稿（草稿允许不合规）；发布要求零错误 + 备注；版本列表、回滚（只生成新草稿）、流程记录。**校验规则必须逐条复刻前端 `pages/workflow/lib/validate.ts:226-385`**（唯一 start / 禁环 / 孤立断链 / 分支出边+兜底 / 空表达式 / 数值条件完整 / 模型库引用存在 / 无回复告警） |
| **M6** | 三场景无阻塞 + A1–A9 全过 + B1–B7 实测值写进验收报告 |

### 4.2 M4 是全表最拥挤的一段，先拆

`04` 把「应用配置 + 发布 + 公开凭证 + 流式问答 + 引用 + 多轮 + 停止/重生成」压在 3 周里，
共 **35 个端点**，且包含全项目最难的单点（SSE 流式契约）。

**拆成 M4a / M4b**，理由是这两半的**耦合面很窄**：M4a 是「写配置」，M4b 是「跑问答」，
两者之间只有"发布后的应用可被问答"这一条连接（通过 `assistantId` + 公开凭证）。

拆开的好处是**关键路径更短**：M4a 可以与 M3 并行（它只依赖模型与知识库存在，不依赖检索质量），
只有 M4b 必须排在 M3 之后。

### 4.3 ★ 版本号规则：**按周发版**（补丁位 = 周，次版本位 = 阶段）

> ⚠️ **先说清一件事，免得又搞出两套编号**：§一 已认账过"两套编号并存是这份计划此前最大的问题"。
> 所以下面三个编号**各有明确角色、互不重叠**：

| 编号 | 角色 | 谁用 |
|---|---|---|
| **M0–M6** | ★ **里程碑：工期与依赖的权威单位** | 排期、关键路径、里程碑验收 |

```
0 . <阶段> . <该阶段内的周序号>
    ↑         ↑
  次版本位     补丁位 = ★ 每周一次的发布（"小步快跑"的落点）
```

- ★ **每周发一个版本**（补丁位递增）—— 每周末必须**可发布**（四条判据见 §4.7.1）

### 7.3 完成定义（DoD，`04:288-296`）

一个功能算"完成"需要满足：① 领域不变量在**应用层与数据库层都有兜底** ② 有自动化测试（领域单测 + 关键链路集成）
③ 失败路径有可读提示、**不存在静默失效** ④ 关键操作有日志与指标埋点 ⑤ 前端按钮已接权限点
⑥ 模块边界校验通过 ⑦ **已在真实语料上手工验证过**。

> 第 ⑦ 条是最容易被跳过的一条。第 ③ 条是本项目**这个会话里已经栽过五次**的那一类 ——
> 「报红会有人修，'少了一条'没人会注意到」。

#### 11.9.3 口径组的"完成"怎么算（防止口径组变成新的黑洞）

口径组的产物统一是**三样，缺一样不算完成**：

1. **一节口径**（写进对应设计册，必须含**取舍理由**与**冲突时谁赢**）；
