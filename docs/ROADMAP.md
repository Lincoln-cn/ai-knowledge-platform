## 一、这份计划的形状

## 二、「可用阶段」的定义

**这是转公开（private → public）的门槛。** 三张清单全绿才算到。

### 2.1 功能清单（端到端场景全部走通）

`04` §三 定义的三个场景，在 `VITE_USE_MOCK=false` 下无阻塞完成：

| 场景 | 内容 | 验证的假设 |
|---|---|---|
| **S1** | 知识运营：建库 → 上传真实文档 → 切分 + 调参 → 向量化（真实进度）→ 命中测试 → 停用分段后不再命中 | H1、H3 |
| **S2** | 应用配置：建应用 → 选模型 → 写提示词 → 绑知识库 → 发布 → 生成公开链接 → 外部访客未登录提问得带引用答案 → 撤销后 1 分钟内失效 | H3、免登录安全 |
| **S3** | 终端用户：流式作答 → 引用可展开溯源 → 连续追问 5 轮 → 生成中停止保留已生成内容 → 重新生成 → 赞/取消赞刷新后仍在 → 会话评分 | 交互完整性 |

### 2.2 数据真实性清单（`04` §6.2 的 A1–A9）

**A2 是最容易被绕过、也最能说明问题的一条**：任意时刻的进度与状态必须与数据库实际状态一致，
**刷新页面不重置**。前端现在的进度是 mock 推进的 —— 这一条通过，就等于"后端真的接管了状态"。

A1 全链路 · A2 状态真实性 · A3 失败可见（人为构造失败，界面给出可读原因与重试）·
A4 引用可溯源 · A5 停止与重生成 · A6 多轮上下文（10 轮仍能指代第 1 轮实体）·
A7 权限生效（前端看不到按钮 **且** 直接调接口被拒）· A8 免登录安全 · A9 模块边界校验通过。

### 2.3 质量与工程清单

| 项 | 门槛 |
|---|---|
| 量化指标（`04` §6.3） | **B1 命中率 ≥70%** · **B2 答案可用率 ≥75%** · B3 引用准确率 ≥80% · **B4 首字延迟：单跳 ≤10s、多跳 ≤20s**（CPU/4B；★ 2026-11-01 用户拍板：**热态**口径 —— 冷启动单列记、不判红，见 `§11.10.79`；★ 2026-11-08 用户拍板：**按场景分开** —— 见 `§11.22`）· B5 完整回答 ≤60s · B6 入库 ≥3 段/秒 · B7 连续 200 次问答无未处理异常 |
| 前端闸门 | `vue-tsc` 0 · 模板配平 · 设计系统维度全 0 · `build:mock` ✓ · 11 个脚本 exit 0 · console 0 |
| 后端闸门 | 架构校验测试通过 · 关键链路集成测试通过 · **契约漂移检测**通过（见 §七） |
| 工程 | **CI（GitHub Actions）跑通**：前端 11 个脚本 + `vue-tsc`/`build` + 后端四类闸门 · `docker-compose.yml` 一条命令起（应用 + PG/pgvector + 模型网关）· 示例数据种子（★ 2026-10-28 已有：`db/seed/V900__sample_business_data.sql`，`SEED_SAMPLE_DATA=true` 打开，见 §11.10.28） |
| 文档 | 面向贡献者的「如何加一个模块」· CHANGELOG 起点 |

> **B1/B2 不达标不是"功能没做完"，而是假设 H1 不成立** —— 此时正确的动作是回机制二（检索策略）
> 与问答对（P2 升 P0）做优化，**不是继续加功能**。这条判断规则写在计划里，是为了在指标不达标时
> 有据可依地不乱改方向。
>
> ★ **这三张清单是 MVP 的唯一定义（范围不加码）** —— 企业级缺口（工具调用与审计 / MCP / 多租户 / 国密 / 备份演练 / 技能市场等）
> **一项都不进这三张清单**：它们要么「**留缝**」（进第 16–18 周但不占功能位）、要么「**只记账**」（Issue 开着、代码不动）。

### 3.5 ★ 权限模型缺了一层：只有「操作」，没有「范围」

**这是本轮发现的、影响面最大的一处设计缺口。** 详细设计见
[`系统设计方案/07-角色与数据权限模型.md`](系统设计方案/07-角色与数据权限模型.md)，此处只记差距。

| # | 事实 | 读数 |
|---|---|---|
| 1 | 权限点 **13 个，全是"操作"** | `knowledge:view` 是**无参数**的 —— 能回答「能不能看知识库」，**回答不了「能看哪些」** |
| 2 | 契约里**归属/可见性字段 0 个** | `owner` / `visibility` / `sharedWith` / `orgId` 全无 |
| 3 | `Role` 类型**没有数据范围的表达位** | 只有 `permissions: string[]` |
| 4 | **旧系统是三层权限**（菜单 + **数据** + 接口，`FR-01-05`） | 新系统只有菜单（路由 meta）+ 接口（权限点）⇒ **数据层丢了** |
| 5 | ⇒ **普通用户看到的是「整个工地，只是按钮少几个」** | `USER` 只有 **2 个权限点**，却看到 **4 个模块**，其中 `知识库` 与 `应用管理` 是**全平台建设面** |

**为什么不能靠加权限点解决**：那是**集合关系**（自己的／被共享的／全平台的），
不是**动作** —— `knowledge:view` 加多少前缀都表达不了。

**处置（已写进 07）**：引入 `ownerId` + `visibility` + `sharedWith`（资源侧）与
`dataScope: own | shared | all`（角色侧），可见性判定**只在后端一处实现**；
并把「普通用户」拆成 **使用者**（纯消费）与 **个人建设者**（能建自己的）两个角色。
`04` 里「MVP 采用全员可见」那条口径**已作废**。

**四件待拍板**（07 §七）：管理员能否看别人的会话 · `CREATOR` 能否建编排应用 ·
`public` 可见性是否进 MVP · 新建资源的默认可见性。**建议四条全选"默认收窄"** ——
数据权限放开容易、收回难。

## 四、里程碑总表
**规模**：后端 2 人 + 前端 1 人 +（兼）测试 1 人（`04:302`）。人力不同按比例缩放。

**覆盖度对账**：前端契约共 **98 个端点**（12 个域 + `POST /auth/refresh`），下表把它们**全部**落到里程碑上。

| 里程碑 | 模块（端点数） | 交付物 | 预计 |
|---|---|---|---|
| **M0 · 骨架** | `platform` 共享内核 + 11 模块骨架（0） | 可启动的空系统 + **架构边界校验测试通过** + Flyway 迁移框架 + 鉴权框架 + CI + **Spring AI 接入验证 + 模型能力探测 + 参数下发核实** | 1 周 |
| **M1 · 身份与模型** | `identity`(11) + `modelcatalog`(8) + `POST /auth/refresh`(1) = **20** | 能登录、能注册并加载一个模型 | 1.5 周 |
| **M2 · 知识库与入库** | `knowledge`(7) + `ingestion`(14) = **21** | **能上传文档并变成可检索的分段** | 3 周 ★关键 |
| **M3 · 检索与命中测试** | `retrieval`(3) + `vectorindex`（基础设施，无对外端点）= **3** | 能看到命中结果并调参 | 1.5 周 ★关键 · ⚠️ **只含"基础检索"**；策略层（改写/扩展/分解/多跳）见 `10 §10.2`，**建议拆 M3a/M3b**（待拍板） |

| **M5 · 反馈与看板** | `feedback`(5) + `analytics`(4) = **9** | 能收集反馈并看到用量 | 1 周 |
| **M5.5 · 编排配置面**（本计划补位） | `workflow`(10) = **10** | 能画流程、存草稿、校验、发布版本、回滚、看流程记录 | 1.5 周 |
| **M6 · 端到端验证与调优** | — (0) | **验收报告（B1–B7 实测值）** | 2.5 周 |

**合计 15 周。** 比 `04` 的 13.5 周多 1.5 周，增量全部来自 **M5.5** —— `04:67` 明说编排配置界面进 MVP，
但它的 §七 里程碑表没有给这一块落位。这是一处真实的范围漏算，不是估算变松。

**关键路径：M2 → M3 → M4b。** 这三段占总量约 60%，且 M2 的分段质量直接决定 M4b 的问答质量。

### 4.1 每个里程碑的验收怎么量

| 里程碑 | 验收口径（可复核） |
|---|---|
| **M0** | ① `ApplicationModules.verify()` 通过；故意加一处越界依赖 ⇒ **构建失败**（金丝雀）② `docker-compose up` 能起空系统 ③ **交付两份结论**：各模型的思考三态取值、Spring AI 能否下发思考开关参数。**这两份结论是 M2 的入口条件**，不是文档 |
| **M1** | 登录成功 + 令牌刷新（401 静默重试一次）+ 权限点下发；注册并加载一个模型 ⇒ 状态从「加载中」变「已加载」（**加载态存服务端**，刷新页面仍在） |
| **M2** | 上传真实文档 ⇒ 状态机走完七态；**A2**：任意时刻进度与数据库一致、刷新不重置；**A3**：人为构造解析/向量化失败 ⇒ 界面给出可读原因与重试 |
| **M3** | 三种检索模式都能出结果；混合模式走 RRF；阈值先于 TopN；命中测试页可调参并看到相似度与来源 |
| **M4a** | 发布校验**两档分化**：简单应用查提示词/检索项，编排应用查「流程已配置」并逐节点校验模型已加载；`published=true` 会重跑校验并拒绝不合格；凭证撤销是终态（不可重新启用） |

### 4.2 M4 是全表最拥挤的一段，先拆

`04` 把「应用配置 + 发布 + 公开凭证 + 流式问答 + 引用 + 多轮 + 停止/重生成」压在 3 周里，
共 **35 个端点**，且包含全项目最难的单点（SSE 流式契约）。

**拆成 M4a / M4b**，理由是这两半的**耦合面很窄**：M4a 是「写配置」，M4b 是「跑问答」，
两者之间只有"发布后的应用可被问答"这一条连接（通过 `assistantId` + 公开凭证）。

拆开的好处是**关键路径更短**：M4a 可以与 M3 并行（它只依赖模型与知识库存在，不依赖检索质量），
只有 M4b 必须排在 M3 之后。

★ 后两道是 0.3.0 补记时补的，**因为它们盯的是既有闸门没覆盖的两类**：

1. **逐页走查**：前三道各管一段流程，回答不了「**把每一页都打开一遍，哪一页是坏的**」——
   而用户报问题的方式恰恰是「这个功能用不了」。分三档记账，避免两种极端：
   · **必须能用**（演示路径，坏了就红）· **已知未落地**（后端还没做，只记录 —— 但**必须真的失败**，
   否则清单会变成永久黑洞）· ★ **页面在、功能未落地**（加载时一声不响，**点主按钮才报**）——
   命中测试页就属于这一档：加载零失败，看着比谁都干净，点「测试」才 404 `/retrieval/test`。
2. **按钮接线**：「页面能打开」**不等于**按钮能用。文档改名/启停/删除、分段启停、逐段重向量这一族
   曾经**全都没有后端端点**，点下去要么 404「接口不存在」、要么 500「服务内部错误」——
   ★ 这类失败**看起来像环境问题**，所以必须有一条闸门从界面点下去、两头对账（界面读了什么 + 库里变成什么）。

### 7.3 完成定义（DoD，`04:288-296`）

一个功能算"完成"需要满足：① 领域不变量在**应用层与数据库层都有兜底** ② 有自动化测试（领域单测 + 关键链路集成）
③ 失败路径有可读提示、**不存在静默失效** ④ 关键操作有日志与指标埋点 ⑤ 前端按钮已接权限点
⑥ 模块边界校验通过 ⑦ **已在真实语料上手工验证过**。

> 第 ⑦ 条是最容易被跳过的一条。第 ③ 条是本项目**这个会话里已经栽过五次**的那一类 ——
> 「报红会有人修，'少了一条'没人会注意到」。

### 11.61.3 unslop 的口径：轻度 slop，改的是语言与层级，不是配色

审计结论：底色/发丝线/圆角/令牌已成系统（`tokens.css` 全 `var(--…)`），**不属于重做级 slop**。真病三类：

1. **内部口径当界面文案**（最重）。实例：模型页顶部整条 `notice info` 讲「思考模式三态而非开关…」；

   知识库建库向导里的 `（13 §6）`；检索页 `实测 +13.9 点 B3（裸检索 57.4% → 生产口径 71.3%）`。
   ⇒ 处置：**结论留给人看，读数进 `title`**。这不是"删信息"，是"把信息放到它该在的层"。

### 11.61.5 两处契约变更（都是**加可选字段**，旧帧形状不变）

### 11.61.7 那一课：`max-chars` 是**硬上限**，不是目标长度

第一次实现 1.3 的「会话附件段更短」时，我把 `conversation-attachment-max-chars`（1200→500）压的是 `max-chars`。
真栈立刻炸：切块器按标点切出的段正好 **501 字** > 500 ⇒ `SegmentService` 抛
「该内容 501 字，超出当前向量模型上限 500 字」⇒ 整篇 `SEGMENT_FAILED`、分段 0 ⇒ 附件**一条都检索不到**。

★ 两个词的差别是全案的关键：
- `max-chars`（1200）= **单段硬上限**，超了就是失败；
- `segment-length`（500）= **目标长度**，切块器朝它努力但会按标点边界浮动。

⇒ 想"段更短"要压**目标长度**，压硬上限等于把内容判死刑。
★ 判据：**凡是"长度/条数/容量"这类可调项，动手前先分清它是"目标"还是"约束"** —— 两者的失败形态完全不同
（目标配小了只是效果差，约束配小了是整篇失败）。

### 11.61.8 `#358`：附件失败态的误归因（用户点名"很关键"）

症状：上传 1250 字附件后问两次不同问法，都只得到「检索跑完了，但知识库里没有与这个问题相关的内容。」
而库里那条文档的真实状态是 `SEGMENT_FAILED`、`fail_reason` = 「该内容 501 字，超出当前向量模型上限 500 字。」

这是一句**听起来完全合理、却把用户指向错误方向的真话** —— 他会去改问法、去翻知识库，谁也想不到要重传文件。
这就是本项目头号病 `silent-failure` 的标准形状。

改法（SPI 最小扩展 + 一处判据集中）：

1. `DocumentStatus.isFailed()`：`SEGMENT_FAILED || EMBEDDING_FAILED`。
   ★ 为什么要有方法而不是让调用方各写一遍：这个判断的用途是"这份内容现在还能不能被检索到"，
   两段各有失败态 —— 散着写迟早漏一个（本次就两个都没看）。
2. `ConversationAttachmentPort.describeAttachmentFailure(conversationId)`：只报两种 ——
   ① 已进失败态（带 `fail_reason`）；② 还在解析中（`PENDING_PARSE` / `SEGMENTING`）。
   ★ **`PENDING_EMBEDDING` 刻意不报**：会话域只走全文一路，没向量化的分段照样能被全文命中
   （实测：状态 `PENDING_EMBEDDING`、6 段、命中 2 条）。把它报成"附件不可用"是另一种假话。
3. `ChatService.noHitNotice(...)`：零命中时若有附件就优先问附件原因，否则沿用原文案。

判据（写进测试）：**零引用且本会话附件检索不到时，`notice` 必须是附件那句话，且不许出现「知识库里没有」**；
同时另有一条反证：**附件正常时文案必须还是原来那句**（否则等于把所有零命中都怪到附件上）。

## 11.62 提示词版本历史（0.9.5 · 一条提示词的「多版本纵向对比」）

> 用户原话（2026-11-19）：**「我倒没想着做多文档对比，我想做的是 在提示词页面的多版本 对比」**。
> 我上一轮误解成"多份提示词横向比"，这条记下纠正后的范围：**同一条提示词，改一次存一版，能看两次之间改了什么、能回退**。

### 11.62.1 为什么做（现象 → 根因 → 危害）

**现象**：`as_prompt_config` 只有 `created_at` / `updated_at`，没有版本。`PromptCatalogService.updateConfig`
最后一句是 `configs.save(config)` —— **原地覆盖**。改一次，上一版永久消失。

**根因**：提示词被当成"可编辑的一段文本"，而不是"一份会被反复改的配置资产"。写过 200–300 字的角色指令都知道，
改一句话之后想不起上一版是怎么写的；改坏了只能凭记忆重写。

**危害**：不是"少个功能"，而是**改动的代价不对等** —— 修改很轻（点一下编辑），回退不可能。
人一旦知道"改了就回不去"，就会倾向于不改，指令于是停在第一版。

### 11.62.2 数据形状

新表 `as_prompt_config_version`（迁移 `V112`）：

```sql
create table if not exists as_prompt_config_version (
  id          uuid primary key default gen_random_uuid(),
  config_id   uuid not null references as_prompt_config(id),
  version_no  int  not null,
  role_name   varchar(64)  not null,
  call_word   varchar(1000) not null,
  type_id     uuid not null,
  description varchar(500) not null default '',
  icon        varchar(16) not null,
  kind        varchar(16) not null default 'ROLE',
  app_id      uuid,
  saved_at    timestamptz not null default now(),
  saved_by    uuid,
  unique (config_id, version_no)
);
create index idx_as_prompt_config_version on as_prompt_config_version (config_id, version_no desc);
```

★ **不把 `as_prompt_config` 改成"版本表 + 当前指针"**：所有读路径（应用配置选词、导出包、对话页提示词内核）
都读当前表，动它会牵连一大片。让当前表继续当"最新一版"，版本表只追加。

★ 迁移动手时把现存 26 条（14 条 `ROLE` + 12 条 `QUESTION`）初始化成 `v1`，`saved_at = created_at`
（否则第一版永远是空的，用户点"版本"看不到任何东西）。

### 11.62.3 写入策略

`PromptCatalogService.updateConfig` 在 `config.update(...)` **之前**追加一版，同一事务：

1. 比较 5 个字段（`roleName` / `callWord` / `typeId` / `description` / `icon` + `kind` / `appId`），
   **全等则不写版本** —— 只点开编辑点保存不该多一版噪声。
2. 否则 `version_no = (select coalesce(max(version_no),0)+1)`，落旧值（改之前的快照），`saved_by = 当前 actorId`。
3. 再执行原有的 `config.update` + `save`。

★ **守卫**：`updateConfig` 连改三次 ⇒ 版本表有 `v1/v2/v3`，且**当前表的值 == `v3` 的值**。
这条能红（把追加逻辑去掉就红），防的是"两处写入漂移"——那比"没有版本"更难发现。

### 11.62.4 接口

```
GET  /prompt-configs/{id}/versions                    → [{versionNo, savedAt, savedBy, preview}]
GET  /prompt-configs/{id}/versions/{v}                → 该版全文（用于 diff 两版）
POST /prompt-configs/{id}/versions/{v}/restore        → 以该版内容生成新一期（v(n+1)），历史不删
```

`GET /versions` 只要列表摘要（`preview` = 正文前 60 字），全文按需取 —— 26 条 × 每配置十几版也不会一次拉爆。

★ **不做** `GET .../diff?from=&to=`：diff 是纯前端渲染问题，后端算完还得传回两份文本，多一层往返；
前端拿两版全文自己算（LCS 按行比，约 50 行）。

### 11.62.5 界面

提示词管理页（`frontend/src/pages/assistants/components/prompts/PromptConfigPanel.vue`）每行操作区加「历史」：

- 抽屉左侧版本列表：`v3 · 今天 22:10 · 管理员` / `v2 · 昨天` / `v1 · 10-15`，默认选中最新两版

★ 令牌纪律：全部走 `var(--color-*)` / `var(--space-*)`；不引 diff 库（依赖白名单里没有，
`frontend/README.md` 要加一条就得写理由，为一个抽屉不值得）。

### 11.62.6 明确不做（两条边界，都是有理由的）

1. **不在提示词页"跑模型看效果"**：角色指令的实际效果 = 这段指令 + 应用绑定的模型 + 知识库 + 检索参数。

   本节的"多版本"指的是**同一条**提示词的纵向历史。

### 11.62.7 验收判据

## 11.63 提示词评测：把「我觉得这样更好」变成可核对的数（0.9.7 规划，2026-11-20）

### 11.63.1 要解决的问题

`§11.62` 做完了"改坏了能退回去"，但**"改得更好还是更差"仍然没有答案**。

现状的判定方式只有两种，都不能用：

- **主观**：作者自己读一遍，觉得更清楚了。改的人就是评的人，而且他刚花时间改 —— 几乎必然觉得更好。
- **模型自评**：把新提示词和旧答案交给同一个模型问"哪个更好"。同源模型有自我偏好，长答案还有长度偏好，读数接近于随机。

危害不在于"判断不准"，而在于**它让人不敢改**：既然改好改坏看不出，那就不改（这一点与 `§11.62.1` 是同一条因果链）。所以评测不是锦上添花，它是"提示词能被持续维护"的前提。

### 11.63.2 四层方案与各层的可信边界

四层按"便宜 → 贵"排列，**每一层只回答它能回答的那部分**，不许拿上一层的读数去推断下一层。

**第 1 层 · 可机械断言的项（零成本，可进 CI）**

角色设定里真正能被机器判的，是它对**形式**的要求：

| 设定里常见的话 | 可自动检查的读数 |
|---|---|
| 「必须标注出自第几条」 | 答案里 `[N]` / `第 N 条` 的出现率 |
| 「不确定就说不知道」 | 「没有提到 / 无法确定」这类表述的占比 |
| 「用列表输出」 | 是否输出了有序/无序列表 |
| 「不超过 200 字」 | 字数分布 |

做法是把每条要求**转成一条断言**（`assert` 文本 + 判据类型 + 期望），跑一遍看通过率。

★ 硬边界：**只覆盖"能被写成断言"的部分**。语气是否得体、判断是否符合业务口径，这一层测不了 —— 不许把它当成"提示词质量分"。

**第 2 层 · 人工盲评（唯一现在就能信的）**

固定一组问题（起步 20 条），两版各跑一次，**打乱顺序**交给 2–3 个人评，评的人不知道哪版是哪版。

- 输出：**胜率** + **评者一致性**（多人时）。
- 读数口径：胜率 < 60% ⇒ 视为无差别，不必改；≥ 80% ⇒ 可信；评者分歧大 ⇒ 这个问题本身有多个合理答案，先别定输赢。
- ★ 必须留「差不多」这一档。只给"更好/更差"会逼人瞎选，数据反而更脏。

**第 3 层 · 模型当裁判（有条件可信，只做初筛）**

用**另一个模型**（不是被测那个）按 rubric 打分。三条控制缺一不可：

1. 裁判模型 ≠ 被测模型（否则是自评）；
2. 顺序随机（消掉位置偏好）；
3. 只看答案、不看提示词（否则它会去"理解意图"而不是评结果）。

已知偏差：长度偏好、家族偏好。与人工评的相关性约 0.6–0.8 ⇒ **能筛掉明显退化的版本，不能用来定"哪个更好"**。

**第 4 层 · 回归集（最值钱、最慢）**

把"这个问题必须答成这样"的样例攒起来（预期要点 + 禁止出现的内容），每次改提示词跑一遍看通过率。与 `10 §7.4` 的问答对、以及语料评测那批是同一套基础设施 ⇒ **不新起一套，合进去**。

### 11.63.3 本版（0.9.7）只做第 1 层 + 第 2 层的最小形态

**数据形状**（4 张表，全部 `on delete cascade` 到提示词配置）

| 表 | 用途 | 关键列 |
|---|---|---|
| `as_prompt_eval_set` | 评测集：一条提示词的一组问题 | `id / prompt_config_id / name / created_at / created_by` |
| `as_prompt_eval_item` | 评测集里的问题 | `id / set_id / ordinal / question / assertions` |
| `as_prompt_eval_run` | 一次评测运行：两个版本 × 全部问题 | `id / set_id / base_version_no / draft_text / status / started_at / finished_at` |
| `as_prompt_eval_answer` | 一次运行里每题的产出与评分 | `id / run_id / item_id / side(SAVED/DRAFT) / answer / elapsed_ms / pass_count / fail_count / assertion_results / verdict(BETTER/SAME/WORSE) / note / scored_by / scored_at` |

★ **已落库**：`V114__as_prompt_eval.sql` 建这 4 张表（全部 `on delete cascade` 到 `as_prompt_config`，`status`/`side`/`verdict` 都有 check 约束，`(run_id, item_id, side)` 唯一）。

★ **已落码**（2026-11-19/20 批 + 2026-11-27 批，全部在 `main`）：`PromptEvalService` + `PromptEvalController`（service/controller + 端点）· 前端评测抽屉 `PromptEvalDrawer.vue` · 断言编辑框 `PromptAssertionsDialog.vue` · 纯函数判定器 `assistant/domain/PromptAssertions.java` · mock 十一个端点 · 验收脚本 `scripts/prompt_eval_check.py`。

**第 1 层断言的数据形状**（`V115__as_prompt_eval_assertions.sql`）：定义挂**题**上（`as_prompt_eval_item.assertions`）、判定结果挂**答案**上（`as_prompt_eval_answer.assertion_results`），两列都是 text 存 JSON（只按"这道题 / 这条答案"整块读写，没有库侧查询需求；要按断言统计时再换 jsonb 是一次新建列迁移，不算返工）。

**断言七种**（每条只比一件事，混在一起就定位不到"哪条要求没被满足"）：`CONTAINS`（必须出现）/ `NOT_CONTAINS`（不许出现）/ `REGEX`（匹配）/ `MAX_CHARS` / `MIN_CHARS`（字数上下限）/ `LIST`（至少两个列表项）/ `UNCERTAIN`（资料里没有时要承认）。★ 判定**不调用模型**：零成本、可离线、可进单测（`PromptAssertionsTest` 10 条）。

★ **三种"零"必须分开**：没设断言（`assertions = []`，返回空结果）/ 设了且全过（每条 `passed=true`）/ 设了且有失败（`detail` 要能单独读明白，例如"没有出现「第七条」"）。把第一种显示成「0 通过 0 失败」等于把"没测"说成"测了且都好"。

★ **改定义不回头改写历史**：断言定义挂题、判定结果挂答案 —— 改一次定义，已经跑完的那次读数是它当时的快照；要看新定义就重跑一次。

★ **发版状态（2026-11-27）**：`0.9.7` 已发版，三处版本号 = `0.9.7`。`§11.63.5` 五条判据**全部在本机真栈（18088）核过**，同一份 `scripts/prompt_eval_check.py --allow-real-model` 输出即为读数：① 两版答案各 2 条（SAVED 2 / DRAFT 2）· ② 胜率 0.75（更好 1 · 差不多 1 · 更差 0，已评 2/2）· ③ 断言可增（保存 2 条读回 2 条，每条有 id）、可删（减到 1 条再清空）、判定一过一败且失败项带 label/detail、改定义后历史运行仍是快照 · ④ 十分钟内 `cv_message` 零新增 · ⑤ 删评测集后 `as_prompt_eval_{set,item,run,answer}` 四表零行。★ 判据 3 能成立的前提是 `V115` 已执行（`flyway_schema_history` 里 `115 | as prompt eval assertions | t`）与 `PUT /prompt-eval-items/{id}/assertions` 已生效 —— 未经重启时脚本会明说"接口不存在"，不会假装通过。

★ `draft_text` **把草稿正文整段存下来**（不引用版本号）：评测常常发生在"还没保存"的那一版上，而一旦保存就变成新版本 —— 存正文才能复现当时到底测了什么。

**行为**

1. 提示词页每行加「评测」→ 抽屉：选评测集（或新建）、选基线版本（默认 = 当前）、显示"草稿 = 当前表单值或最新版"。
2. 点「开始」⇒ 后端按 `set_id` 逐题跑两次（`saved` 用 `base_version_no` 的正文、`draft` 用 `draft_text`），**复用 `ChatService.debugCompare` 的同一条只读路径语义**（不写会话、不写消息）。
3. 结果表：每题一行，两版答案并排 + **每条断言的判定明细**（失败项要写清是哪一侧、哪条断言、为什么没过）+ 人工三档（更好 / 差不多 / 更差）。
4. 汇总：**胜率** = (更好 × 1 + 差不多 × 0.5) / 已评题数；断言通过率单列（**两侧答案各判一遍再累计** —— 基线那版也在产出答案，凭什么只测草稿）；未评题数必须显示（不许把没评的当"差不多"）。
5. 题目列表每行有「断言 N」入口（N = 当前条数，0 条时是灰的）→ 打开断言编辑框：加一条 / 改类型 / 改值 / 起名 / 删一条，**整张表一次保存**（断言是一组互相配合的判据，逐条即时保存会留下"改了两条、第三条没存"的半截状态）。

**成本与并发**：一次评测 = 2 × 题数 次模型调用。题数上限 30，超过要求分批（避免一次点下去几分钟没反应）。运行状态用 `status` 落库，前端轮询（不做 SSE：这是一次性任务，不是对话）。

### 11.63.4 明确不做

- **不做一键优化**（让模型直接改写提示词）：没有裁判就没有方向，见 `§11.63.2` 第 3 层的边界。
- **不做自动应用**：评测结论永远只是结论，改不改由人按。
- **不在本版做模型裁判**：等人工评真跑过两轮、知道人怎么评了再上，否则无法校准。
- **不做跨提示词横向比**（把 12 条提示词排个名）：它们服务于不同任务，排名没有意义。

### 11.63.5 验收判据（缺一不可）

1. 一次评测跑完，**每道题都有两版答案**，且两版用同一个问题、同一个模型、同一批检索结果。
2. 人工评三档可存、可改、可清空；汇总里的胜率**随已评题数变化**，未评题数单独显示。
3. 断言判据可增删；某条断言判错时，读数里能看出是"哪道题哪条断言"。★ **可核对的形状**：`PUT /prompt-eval-items/{id}/assertions` 整表替换 → 读回条数一致；跑完那次运行的答案行里带 `assertionResults`（每条有 `assertionId / label / kind / passed / detail`）；失败项的 `detail` 能单独读明白（"没有出现「X」"而不是只有 `false`）。★ 验收脚本用**同一个不可能出现的串**挂两条方向相反的断言（`CONTAINS` 必败 + `NOT_CONTAINS` 必过）—— 它们互为反证：实现如果把 `NOT_CONTAINS` 判反了，两条会同真同假，而"一过一败"只在判定真的分开时成立。
4. 评测运行**不产生任何** `cv_conversation` / `cv_message` 行（与调试同一条判据）。
5. 删掉评测集时级联删掉题、运行、答案，不留孤儿。

### 11.63.6 版本规划

- **0.9.7**：本节 11.63.3 的形态（4 张表 + `V115` 两列 + 评测抽屉 + 断言编辑框 + 人工三档 + 胜率汇总 + 第 1 层七种断言完整实现）。★ 第 1 层是**完整实现**、不是占位：定义可增删改、判定七种、失败项能定位到题与断言（`#364` 因此关闭）。
