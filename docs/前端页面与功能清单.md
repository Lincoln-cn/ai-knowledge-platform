# 前端页面与功能清单 —— 到「可用」

> **顺序**：先把前端做到可用，**再按这里列出的接口需求做后端**。
> 每一行「需要的接口」就是后端的输入 —— 本工程现在**只有 mock**（`src/mock/` 是后端的替身），
> 所以这一列不是"对照代码抄的"，是**从前端真正需要什么倒推出来的**。
>
> 来源：13 个模块逐页勘察（4 路并行），每一条都带**文件:行号**证据。
> 判据不是"功能不够丰富"，而是 **走不下去 / 走错了不知道 / 出错了没提示 / 刷新后状态丢了**。

---

## 一、「可用」的判据（三条，可复核）

1. **每轮动作都有终态** —— 界面上不存在"永远加载中""永远生成中"；
   请求失败与"没有数据"**必须能分清**（现在多处把错误渲染成空态）。
2. **刷新与直链不丢状态** —— `?kb=` / `?tab=` / `?conversationId=` / 筛选 / 分页都能恢复；
   会话与消息**刷新后能原样回放**。
3. **入口与接口一致** —— 看不到的入口，直连也不通（权限点 **且** 数据范围）；
   反过来，界面上给出的入口**不能通向 403**。

## 三、P1（不修会被用户撞见，摘要）

**普遍项（几乎每个列表页都有）**：请求失败无 `catch` ⇒ 静默（`models`/`analytics`/`feedback`/`knowledge` 全线）·
筛选/分页**不入 URL** ⇒ 刷新即丢 · 切换筛选**不重置 `page`** ⇒ 停在空页 · `ElMessageBox.confirm` 的取消拒绝未接住 ⇒ unhandled rejection。

**对话**：引用不可回溯（`SourceRef` 无 `segmentId/documentId/kbId`，"跳转到分段"的参数无人读，`?doc=&segment=` 是**死参**）·
空回答无提示 · 重生成/继续**污染上下文**（chat 请求体无 `messageId`）· 长会话截断（固定 `size:100` 无加载更多）· 历史无搜索与分页。

**知识库**：分段列表**不限定知识库**（`GET /segments` 不带 documentId 时返回**所有可见库**的分段 ⇒ 批量删除会**跨库**）·
批量删除是 N 次单删串行、无部分失败回执 · 上传无大小/数量校验与部分失败回执 · 设置面板改动**静默丢失**（切 Tab 即卸载）·
新库检索参数 404 后回落硬编码值 · 命中测试失败**不清理上一次结果**（会把旧结果当这次结论）· 全局进度条把"加载失败"显示成"暂无文档"。

**应用**：`ApiKeysPanel` 的"停用"是**死按钮**（契约无单条启停）· 导出的 bundle **不含 `workflow` 流程定义**（编排应用导出再导入流程为空）·
`fetchList` 无 `catch` · 对话页跳 `/assistants?focus=` 但**列表不读该参数** · 消费者形态不强制 `published=true`（共享的草稿也进广场）。

**外壳/配置**：`loadProfile()` 失败被 `.catch(() => {})` 吞掉 ⇒ 令牌过期落到 `/` 时**顶栏显示"未登录"、菜单塌到 2 项、无提示**·
**可以编辑自己的角色**（管理员把自己改成普通用户 ⇒ 自锁，删自己已挡、改自己未挡）· 可裁掉自己角色的 `system:manage` · 切角色**静默丢弃未保存的勾选** · 用户下拉无「修改密码/我的账号」· 404 页在**壳外**（登录用户敲错 URL 会失去顶栏与一切入口）。

## 六、应用广场的设计（回答「是不是别人共享出来的」）

**你猜得对，而且契约已经有一半了。** 广场应该是**三个来源并存**，不是"只有别人共享的"：

| 来源 | 判据 | 说明 |
|---|---|---|
| **官方应用** | **`Assistant.builtin === true`（契约已有）** | 平台预置（如「通用知识问答」），所有人可用，**只有管理员能改** |
| **他人分享** | `ownerId !== 我` 且对我可见 | 分两档：**公开**（`visibility:'public'`，全平台可发现）· **定向**（`visibility:'shared'` + `grants` 指定账号或角色） |
| **我的应用** | `ownerId === 我` | 自己建的 |

**分享两档 = 你说的那两条**，而且**已经落在 07 册的模型里**（§3.1 + §8.1）：
- **公开** ⇒ `visibility: 'public'`
- **对别人的账号** ⇒ `visibility: 'shared'` + `grants: [{ subject:{kind:'user'|'role', id}, actions:[…] }]`

**好消息**：`builtin` 契约已有 ⇒ **官方应用不需要改契约**；`visibility`/`grants` 的**读**也已在阶段 1 落地。
**坏消息**：分享是**写**，而阶段 1 只加了可选*响应*字段 ⇒ **必须补写接口**（见 §五）。

**建议的页面结构与交互**：
1. 列表顶部加**来源分段**：全部 / 官方 / 共享给我 / 我的（`origin` 可用 `builtin`+`ownerId` 客户端分流，或后端加参数）
2. 卡片来源徽标三态：`官方` / `由 X 分享` / `我的`
3. 卡片主操作**按来源分化**：官方 → 只能「开始对话」；他人分享 → 「开始对话」；我的 → 「配置／分享／概览」
4. **分享对话框**（从卡片或概览抽屉打开）：先选**公开 / 定向**，定向再选主体（账号或角色）—— 保存走 `PATCH visibility` + `PUT grants`
5. 消费者形态**默认只列 `published = true`**（现在共享的草稿也会进广场，与空态文案自相矛盾）

## 七、按页面的「到可用」定义（验收口径）

| 模块 | 「可用」的判据（≤3 条） |
|---|---|
| **对话** | ① 每轮问答都落库：发送/停止/失败三种结局服务端都有记录，刷新与直连 URL 能原样回放消息与引用 ② 流式四种收尾（已生成/已停止/失败/连接异常）**都有终态**，界面上不存在"永远生成中" ③ 分享链路闭环：真实生成（含有效期与权限校验）→ 复制 → 过期/撤销后公开页给出可读原因 |
| **知识库** | ① 两条主链从头走到有结果且**断点可续**：建库→上传→切分确认→向量化（离开再回来看到真实进度，失败可从断点重试）；列表→文档→分段→编辑→**重新向量化**→命中测试能检索到改动后的内容 ② 任何接口失败**就地可见**（错误态与空态严格区分），刷新/直连恢复同一状态 ③ 入口"看不见"与"直连接口被拒"一致 |
| **应用** | ① 广场能回答"**这应用是谁给的、我能不能用**"：三来源可见可筛，点进去就能对话；分享两档可写、可改、可撤销 ② 主链走通且可续：新建→配置→**校验失败能就地改**→发布→生成的链接**真能打开** ③ 每个异步面都有空态/加载态/错误态，失败必须出话 |
| **配置与运营** | ① 每个列表页在"**请求失败**"与"**没有数据**"之间能分清，并给可行动的重试 ② 不存在通往 403 的入口，且危险操作不可自毁（改自己角色/裁自己权限有拦截） ③ 账号闭环成立：`mustChangePassword` 真跳改密页，外壳有改密入口，角色管理能配 `dataScope` |

## 八、长任务状态：从轮询到推送（已拍板要做的机制）

> 起因：使用者的判断 —— *「模型页面定时刷新也没有太大意义，能不能通过后端的 SSE 接口来更新中状态？
> 如果前端断联，后端直接更新数据状态是否可行」*

### 8.1 先把两件事分开（这是本节最重要的一句）

这两点经常被当成一件，其实是正交的：

| | 是 | 怎么定 |
|---|---|---|
| **任务的推进** 依不依赖前端连接？ | **不依赖** | 这不是"是否可行"，是**本来就该这样**。`03` 册已写「进度唯一真相源在后端」，`ingestion` 的进度就是服务端推进的 |
| **状态的读取** 用轮询还是推送？ | 用推送更好 | 纯体验/成本问题，改动面小，但要做对（见 8.3） |

★ **但契约有个真缺口**：现在只写了「有进行中任务时前端才轮询」，**没有写「任务不依赖前端连接」**。
**一条没写进契约的保证，后端可以合理地实现成"连接断了就停"** ⇒ 必须显式补上（见 8.4）。

### 8.2 现状与它带的两个 bug

现在 `/models` 与知识库入库都用 **1.5 s 轮询**（`setTimeout` 自链、只在 `running` 时起表）。
它**能用**，但带两个真缺陷：

1. **没有上限与退避** —— 后端若卡在"加载中"，页面会**无限**每 1.5 s 打一枪
2. **只扫当前页** —— `/models` 的轮询只刷新当前页的模型，**第 2 页的"加载中"永远不会更新**

### 8.3 推送要做对的四件事

| 要做对 | 为什么 |
|---|---|
| **通知 ≠ 真相** | SSE 只发"变了"，真相永远靠一次 REST 补齐。**重连后必须先补拉一次当前状态** —— 否则断连期间的变更全丢 |
| **心跳** | 企业内网的 nginx/网关常配 60 s 空闲超时 ⇒ 没心跳就被掐断。**复用 chat SSE 的注释帧**（`:` 开头；现有 `splitFrames` 已经会跳过它） |
| **降级轮询** | SSE 连不上要能回落到"页面可见时才轮询"，且**轮询必须有上限与退避** |
| **一条通用任务流** | 不是每个模块开一条，否则前端要管 N 个连接，多标签页还会翻倍 |

**栈上可行**：ADR-01 选的是 **Spring MVC + 虚拟线程（不是 WebFlux）**——
虚拟线程下一连接一线程很便宜，SSE 完全在已选定的栈内。

### 8.4 接口需求

| 接口 | 方法 + 路径 | 请求 | 响应 | 说明 |
|---|---|---|---|---|
| 任务事件流 | `GET /events/stream` | 可选 `resources=model,ingestion` | SSE，帧格式沿用现有 `event`/`data` | 一条流覆盖全部长任务 |
| 事件内容 | — | — | `{ resource: 'model'\|'ingestion'\|'assistant', id, status, progress? }` | 前端按需订阅/忽略；带资源标识才能在一条流上区分 |
| **不依赖连接的保证** | 契约注释 + 后端行为 | — | — | **任务在服务端推进，与前端连接无关**；断联只影响"看到" |

### 8.5 与"可用"的关系（务实的排序）

**这件事不属于"不可用"** —— 现在轮询能用，只是浪费且有两个 bug。
所以排序建议是：**先修那两个 bug（加上限与退避 · 跨页刷新），把 SSE 排到前端 MVP 之后**。
理由：SSE 替掉轮询需要**后端配合**（新端点 + 事件语义），而当前明确的目标是"**前端先到可用**"。
