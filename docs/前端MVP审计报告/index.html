前端 MVP 交付审计报告

问题不是「功能够不够丰富」，而是 真实用户走不走得下去、走错了知不知道、 出错了有没有提示、刷新后状态丢不丢。本报告按这四条复核。

01结论

可以按前端约定的接口开始开发后端 Server 服务。

  • 18 个 P0 全部收口，P1 全部收口 —— 逐条有可执行断言，不靠自述。
  • 四个角色的业务组合各自跑得通：顶部导航、路由可达性、页面动作三层互相一致， 没有「看得见但点进去 403」，也没有「界面给了入口但按钮不存在」之外的意外。
  • 数据范围真的生效：同一页面对不同角色返回不同数据量（普通用户只看得到 3 个应用 / 2 条会话， 全平台口径角色看得到 5 / 6）。
  • 契约面已定型且可枚举：12 个域、115 个端点、全部从 @/api 单一出口导出； 清单里当初倒推出的 22 条接口需求，绝大多数已经作为可选字段 / 新端点写进契约。

收口后已无在飞项：本报告初版列出的 7 条缺口全部已修并逐条验证； 收口过程中闸门又抓出 4 个真缺陷（编排画布节点菜单、模型弹窗首开空目录、/admin 的 Tab 与 URL 单向同步、/prompt-configs 写接口无门禁），也都已修 —— 详见 §8。

05角色 × 功能：完整业务组合

09后端开工建议

可以开工。以下是让前后端一次对接成功的几条硬约束 —— 它们都是从这次审计里量出来的，不是猜的。

必须遵守的契约纪律

  • 响应包络：新链路的响应是单层（{ code, message, data }，页面读 data）。 但画布的旧调用点读双层（res.data.data）—— 这一层差异由 api/legacy/setting.ts 吸收， 后端只实现单层，不要在两端之间摇摆。
  • 分页形状：一律 { list, total, page, size }（PageResult）。
  • 错误语义：看不见的资源一律返回 404 而不是 403（403 等于确认 id 存在）。 前端已经把「请求失败」与「没有数据」分成两个渲染分支，请给可区分的错误码。
  • 列表必须服务端按 dataScope 过滤：前端隐藏入口只是体验，不是安全边界。 审计实测的读数是后端过滤的验收目标 —— 普通用户的 /assistants 应只见 3 个、会话 2 条。
  • 幂等：POST /knowledge-bases 认 clientRequestId，重复提交返回既有资源而不是报「名称已存在」。
  • 可选字段只加不删：本次前端为了不破坏既有调用方，一律用「加可选字段 / 新开一个导出」的方式扩展 （例：uploadDocuments 保留 DocumentItem[]，新开 importDocuments 返回 { accepted, rejected[] }）。 后端同一原则：不改变既有字段的类型或含义。

建议的实现顺序

按仓库里的 docs/ROADMAP.md（十节 · M0–M6 · 98 个端点落位 · 关键路径 M2 → M3 → M4b）。 其中三件事值得优先，因为前端已经把它们当既成事实在用：

  1. M1 身份与权限 —— 没有它，前面测到的「角色 × 功能矩阵」全都无法在后端重现。
  2. SSE 流式问答（M4b 的核心） —— 全工程最难的单点。契约里的三态 （已生成｜已停止｜失败）与「error 后仍走 done」必须严格实现， 前端已按这个语义写死了终态处理。
  3. 知识库入库流水线（M2–M3） —— 前端已按「暂存上传 → 按文件预览 → 带计划导入 → 三种重向量化」 的形态写好，接口形状不能改。

切后端时前端要做的唯一一件事

把 VITE_USE_MOCK 置为 false。mock 只住在传输层 （src/mock/handlers/** 与 src/lib/http 之间的分派）， 页面代码、路由、权限判据一行都不需要改。这正是这套架构当初立下的承诺，本次审计确认它仍然成立。
