## 一、先划清边界：记忆不是"聊天记录的另一个副本"

这是本节最重要的一条，因为它决定了后面所有的取舍。

| 东西 | 存在哪 | 谁写的 | 用途 | 能不能被改写 |
|---|---|---|---|---|
| **原始消息** | `cv_message` | 用户与模型 | 记录**发生过什么**（审计、回溯、重新生成） | **永不改写** |
| **记忆** | `cv_memory` | 抽取器 / 做梦任务 | 决定**下一次带什么进 prompt** | 可以合并、可以标 `superseded`、可以软删 |
| **画像** | `cv_user_profile` | 做梦任务 | 整段注入的"这个人是谁" | 每次做梦重算 |

★ **三条由此推出的硬约束**：

1. **做梦只改记忆，绝不改 `cv_message`。** 记忆被合并错了，还能回原始消息重新抽；消息被改了，就永远查不清"它当初凭什么这么记"。
2. **记忆是"提炼过的结论"，不是原文片段。** 所以写入时 `content` 截到 2000 字（`Memory.create` 里做），而不是把整段对话存进去 —— 存原文会让记忆变成第二份消息表，还多一份要维护的一致性。
3. **记忆的缺失不能变成报错。** 记忆是增强项：查不到、向量化失败、做梦任务挂了，都必须退化成"这次对话只是没有记忆"，而不是"这次对话失败"。这一点写在 `MemoryService` 的每个对外方法的契约里。

## 二、四层结构：不是分类，是两种不同的生命周期

用户的原话是"用户 → 用户的对话 → 通用人格化 → 跨会话"。把它落成枚举时，**每一层都对应一个具体的分歧点**，而不只是一个标签：

| 层 | `code` | 回答什么问题 | 召回范围 | 生命周期 |
|---|---|---|---|---|
| `USER` | `user` | 这个人是谁（部门、角色、职责范围） | 跨所有会话 | 最慢变化，通常由管理员或首次对话建立 |
| `CONVERSATION` | `conversation` | **这一次**对话在谈什么 | **只当前会话** | 跟会话绑定；会话删了就该失效 |
| `PERSONA` | `persona` | 他怎么说话、在意什么、忌讳什么 | 跨所有会话 | 由多次对话聚合，只有当画像重算时才变 |
| `CROSS_SESSION` | `cross_session` | 别处谈过、这里还用得上的事实 | 跨所有会话 | 最容易被"做梦"合并与遗忘 |

### 2.1 为什么"层"必须进数据库而不是"按 kind 推出来"

一个自然的想法是：`kind=FACT` 就是跨会话，`kind=SUMMARY` 就是会话级。**这个映射不成立**：

- "这次谈的是 A 项目的预算"（`kind=FACT`，但只在这次会话有意义）
- "他习惯先要结论再要依据"（`kind=PREFERENCE`，但跨所有会话）

⇒ **同一 kind 会在不同层出现**，所以 `level` 必须是独立的一列，并且要有约束保证它和 `scope_id` 一致：

```sql
-- V101 关键约束：分层在数据库里的实际含义
constraint chk_cv_memory_scope check (
  (level = 'conversation' and scope_id is not null) or
  (level <> 'conversation' and scope_id is null)
)
```

没有这条，一张表里混着"这次会话的事"和"这个人是谁"，召回时要么把会话细节带进下一次无关的对话，要么把人物画像丢掉 —— 而且这两种错误**都不会报错**，只会让回答慢慢变得"答非所问"。

### 2.2 为什么画像单独建表

`cv_user_profile` 的字段是**结构化的**（`tone` / `domains[]` / `taboos[]` / `summary`），召回时是**整段注入**；而 persona 层的记忆是一条条可增删的事实。

如果硬把画像做成"`level=persona` 的一条记忆"，就只能用一行文本冒充一个结构，而且每次重算画像都要先找到那一行、删掉、再写一行 —— 中间任何一步失败，画像就空了。单独建表后，重算是**一次 upsert**，原子且可重跑。

## 三、存储：为什么不引入服务，为什么自己写 PG 实现

### 3.1 开源方案的可借鉴与不可用

| 方案 | 结论 |
|---|---|
| **mem0**（Apache-2.0） | ★ 能跑在 PG + pgvector 上，但形态是**独立 Python 服务**（`add()/search()` 走 HTTP）⇒ 撞"不额外增加服务"这条硬约束。**它的设计可借鉴（尤其是"抽取 → 去重 → 冲突消解"三段），代码不可用。** |
| **Spring AI `ChatMemory`** | ✅ **已在依赖树**（`spring-ai-model`）。接口只有三个方法：`add(String, List<Message>)` / `get(String)` / `clear(String)`。官方 `MessageWindowChatMemory` 只在**内存**里留最近 N 条；存储实现官方只给了 Redis / Cassandra / MongoDB ⇒ **没有 JDBC/PG 实现，自己写一个正好。** |
| **LangChain / LlamaIndex 的 memory** | Python 生态，不适用。 |

### 3.2 结论：`ChatMemory` 接口 + 自写 PG 实现 + `cv_memory` 扩展字段

`ChatMemory` 的 `get(conversationId)` 只回答"这个会话的最近 N 条"，**回答不了"这个人是谁"和"跨会话的事"**。所以本设计的做法是：

- **`ChatMemory` 那一层**由 `MessageWindowChatMemory` 之外的新实现承担（会话内的窗口，按条数），**保持现状**（`historyBefore` 不动，`#296` 不替换它）。
- **记忆层**（`cv_memory` / `cv_user_profile`）是**独立于 `ChatMemory` 的一条路**，由 `MemoryRetriever` 负责，产出的是"要拼进 system prompt 的几段文字"。

⇒ 这是一个刻意的决定：**不把记忆伪装成"更多条消息"**。伪装会让"消息"这个概念的语义（`role` / `content` / `feedback`）被污染，而记忆没有 `role`，也不该出现在 `cv_message` 的翻页里。

### 3.3 向量存哪：`cv_memory.embedding`，不走 `vec_embedding_384` sidecar

| 方案 | 评价 |
|---|---|
| 加进 `vec_embedding_384`（与 `kb_segment` 共用） | ❌ 那张表的索引是 `metadata->>'kb_id'` 的语义，记忆没有 `kb_id`；混进去要么破索引语义，要么加一堆 `where kind='memory'` 让两边都变慢 |
| **`cv_memory` 上直接一列 `vector(384)`** | ✅ 记忆的总量是**每人几十到几百条**，量级与 `kb_segment` 的 5520 段完全不同，不值得为它单独做 sidecar |

★ 维度写死 384 是因为当前启用的 embedding 模型是 `multilingual-e5-small`。**换模型要改列类型**，这一点写进 `#296` 的注释（与 `vec_embedding_N` 的 four-table 方案相比，这是"少一个灵活性、少一堆复杂度"的取舍）。

★ `embedding` **可空**：向量化失败不阻断写入。召回时先按"结构化条件"（层 / 重要度 / 时间）过滤，再对**有向量**的那批做相似度排序 —— 没有向量的记忆仍能靠重要度与新鲜度被召回。

## 四、表结构（`V101__conversation_memory.sql`）

### 4.1 `cv_memory`（主表）

| 列 | 类型 | 含义 | 为什么需要它 |
|---|---|---|---|
| `id` | `uuid` | 主键 | |
| `owner_id` | `uuid` | 归属用户 | ★ **只有本人可见**，不做共享 —— 记忆天然是私人的 |
| `level` | `varchar(16)` | 四层之一 | §2 |
| `scope_id` | `uuid` | 会话 id（**仅 CONVERSATION 层**） | 会话级记忆的归属 |
| `kind` | `varchar(16)` | `FACT/PREFERENCE/CONSTRAINT/GOAL/EVENT/SUMMARY` | 决定做梦里怎么合并（同类才能合并） |
| `content` | `text` | 提炼后的结论（≤2000 字） | |
| `source_message_ids` | `uuid[]` | 从哪几条消息抽出来的 | ★ 可回溯：记忆错了要能查回原文 |
| `importance` | `smallint` | 1–5，默认 3 | 召回排序的第一顺位（比相似度更稳） |
| `confidence` | `real` | 0–1，默认 1.0 | 抽取器的把握；低置信度不参与注入 |
| `dedup_key` | `varchar(128)` | 去重键（如 `level:kind:归一化后的主谓`） | 让"重复说同一件事"不产生第二条 |
| `hit_count` / `last_hit_at` | `int` / `timestamptz` | 被召回次数与最后一次 | ★ 做梦"遗忘"的唯一依据 |
| `expires_at` | `timestamptz` | 到期时间 | 会话级记忆的过期 |
| `superseded_by` | `uuid` | 被哪条取代 | ★ **不物理删**：冲突消解要留痕迹 |
| `embedding` | `vector(384)` | 可空 | §3.3 |
| `deleted_at` | `timestamptz` | 软删 | 用户手动删的记忆 |

索引（每条都对应一个具体查询，不为"以后可能用"建）：

| 索引 | 支撑的查询 |
|---|---|
| `idx_cv_memory_recall(owner_id, level, importance desc, updated_at desc) where deleted_at is null and superseded_by is null` | 召回的主查询（先按层与重要度粗筛） |
| `idx_cv_memory_conversation(scope_id)` | 会话级召回 |
| `uq_cv_memory_dedup(owner_id, level, kind, dedup_key) where dedup_key is not null and deleted_at is null` | 写入时的去重（`INSERT ... ON CONFLICT` 的落点） |
| `idx_cv_memory_expiring(expires_at)` | 做梦时的过期扫描 |
| `idx_cv_memory_embedding`（hnsw，`where embedding is not null`） | 相似度排序 |

### 4.2 `cv_user_profile`（画像，一人一行）

`user_id pk` · `tone` · `domains text[]` · `taboos text[]` · `summary` · `source_memory_ids uuid[]` · `updated_at`。

`source_memory_ids` 是画像的可追溯性：**画像里的每一句都该能指出它来自哪几条记忆**，否则重算时无从判断"这条画像是不是还成立"。

### 4.3 `cv_memory_setting`（单行，全局设定）

`enabled`（默认开）· `min_importance`（3）· `recall_limit`（5）· `inject_profile`（开）· `dream_cron`（`0 40 3 * * *`）· `forget_after_days`（90）· `updated_at` / `updated_by`。

写法与 `cv_chat_settings` 一字不差（`id boolean primary key check (id)` + 单行 insert），因为它解决的是同一个问题：**"配置要有唯一一份"**。

## 五、写入：什么时候记、记什么

### 5.1 三个触发点

| 时机 | 层 | 做法 |
|---|---|---|
| **每轮对话结束**（用户消息落库后） | `CONVERSATION` + 可能的 `USER`/`CROSS_SESSION` | 异步抽取：拿最近 2–4 条消息，让模型判断"这里有没有值得长期记住的事"，输出结构化候选 |
| ~~会话结束/长期无活动~~ | ~~`CONVERSATION` → `CROSS_SESSION`~~ | ★ **已删除**（2026-11-16）：与"会话层只放约定"（§5.4）冲突 —— 约定按定义不会跨会话成立，把约定升上去等于让它在下次对话里继续生效，而用户完全不知道。会话层因此没有"可提升"的内容 |
| **夜间做梦** | `PERSONA` + `CROSS_SESSION` + `USER` | §七 |

★ **抽取是异步的、失败不报错**：对话已经答完了，记忆没抽出来只是"下次少记得一点"。如果做成同步，模型抖动一次用户就看到一个失败提示，而这个失败对他的当下毫无意义。

### 5.4 会话层只记约定（2026-11-16 定案）

抽取器只往会话层写 `CONVENTION`（"这次对话按含税口径算""后面都用表格"），迁移 `V102` 的
`chk_cv_memory_convention_scope` 把这条钉在库里：`CONVENTION` 只许出现在会话层，
且会话层只许出现 `CONVENTION`。

★ 为什么不做"会话摘要"：摘要是"这段时间聊了什么"，它属于**消息**的职责（`historyBefore`
本来就在做，而且用的是原文）。再存一份摘要会让同一段对话有两个版本，而两个版本一定会漂。

### 5.2 抽取的输出形态（而不是让模型自由发挥）

```json
{ "kind": "PREFERENCE", "level": "cross_session",
  "content": "偏好先看结论、再看依据", "importance": 4, "confidence": 0.8,
  "dedup_key": "先结论后依据" }
```

三条硬要求写在提示词里：
1. `content` 必须是**陈述句**（"他偏好 X"），不能是对话片段；
2. 拿不准就给低 `confidence`，**不要为了"多记"而猜**；
3. 用户明确表示"记住这个"时 `importance = 5`。

### 5.3 去重：`dedup_key` + 唯一索引，而不是"写之前先查一下"

"先查再写"在并发下会写出两条（两个请求同时查、都查不到、都插入）。用 `uq_cv_memory_dedup` + `INSERT ... ON CONFLICT DO UPDATE SET hit_count = hit_count + 1` 才是原子的。

`dedup_key` 的构造方式决定了去重的粒度，所以它由**代码生成、模型不参与**（模型给的键会因为措辞差异永远撞不上）。

## 六、★★ 运行时分层召回（本册的核心）

### 6.1 召回发生在哪一步

```
用户提问
  → 检索知识库（10 / 11 那条路，不变）
  → 【新增】召回记忆（本节）
  → 组装 prompt：system(角色 + 画像 + 记忆) + 最近 N 条消息 + 检索结果 + 用户问题
  → 生成
```

★ 顺序不能反：**记忆先于消息窗口**。现在 `historyBefore` 取最近 20 条，如果记忆放在它之后，20 条一满记忆就没了 —— 而"用户是谁"恰恰是那 20 条里最不容易出现、又最该一直带着的东西。

### 6.2 分层的召回规则（四条，各不相同）

| 层 | 查询 | 条数上限 | 为什么是这些参数 |
|---|---|---|---|
| `USER` | `owner = ? and level = 'user' and superseded_by is null`，按 `importance desc, updated_at desc` | 3 | "这个人是谁"是**固定背景**，宁可少带也不要带错；不按相似度排（它是前提，不是候选） |
| `CONVERSATION` | 同上 + **`scope_id = 当前会话`** | 5 | ★ 必须带 `scope_id` 过滤；不带就等于把别的会话的细节混进来 |
| `PERSONA` | 同 `USER` 的范围 | 3 | 与画像互补：画像是"整体判断"，persona 记忆是"具体偏好条目" |
| `CROSS_SESSION` | 先按结构化粗筛（`importance ≥ min_importance`），再对**有向量**的做相似度排序 | 5 | 这一层最依赖"相关"：别的会话谈过的事，只有与当前问题相关才值得带 |

**合计上限 = `recall_limit`（默认 5，可在设置里改到 1–20）** —— 不是每层各 5 条加起来 16 条。粗筛出来的候选按 `level 权重 × importance × 相似度` 排序后取前 N。

★ 层权重（`cross_session` 与 `conversation` 高、`user` 与 `persona` 低）的理由：**用户与人格化是"恒定背景"，会话与跨会话是"这次用得上"**。恒定背景占了配额，会话细节就进不来。

### 6.3 与现有 `historyBefore` 的关系（不改它，只管补它）

现状（`ChatService.java:786`）：

```java
turns.historyBefore(conversationId, userMessageId, historyLimit)   // 默认 20 条
```

本设计**不动这条**，理由：
- 它解决的是"最近的对话内容"，用的是**原文**，保真度最高；
- 记忆解决的是"20 条之外、以及跨会话"，用的是**提炼**，保真度低但覆盖广。

两者都有才完整。**如果哪天要压 token，先压记忆（它有 `importance` 可排），不要先压消息** —— 消息是事实，记忆是摘要。

### 6.4 装配成什么样（token 预算怎么切）

```
[角色与规则]                                  ← 既有，不动
[关于这位用户]                                ← 画像 summary（≤ 300 字，整段注入）
  · 他偏好先看结论再看依据（重要度 4）        ← PERSONA / CROSS_SESSION 各若干条
  · 他在安全生产领域，问的多是处罚与期限（重要度 4）
[这次对话的上下文]                            ← CONVERSATION 层
  · 这次在核对消防法的处罚条款（重要度 3）
[最近的消息]                                  ← historyBefore 既有
[检索结果]
[用户问题]
```

★ 预算：记忆段整体上限 `MIN(1200 字, 剩余预算的 15%)`。**硬上限用字数而不是条数**，因为一条记忆可能 20 字也可能 200 字，"最多 5 条"约束不住长度。

### 6.5 降级与失败（记忆不许拖垮对话）

| 失败 | 表现 | 处理 |
|---|---|---|
| 设置里 `enabled = false` | 整段不注入 | 直接跳过，**不查库** |
| 设置表那一行读不到（迁移没跑） | 没有配置 | 用代码默认值 + **WARN 说清"正在用默认值"**（与 `RetrievalEngineSettingsStore` 同一套写法） |
| 召回查询抛异常 | 记忆为空 | `WARN` + 继续生成。**记忆是增强项** |
| 某条记忆向量为空 | 该条不进相似度排序 | 仍可按重要度参与（§3.3） |
| 画像为空 | 只有 persona 记忆 | 正常，新用户本来就没有画像 |

### 6.6 判据（可核对）

1. **分层生效**：构造两条不同会话的 `CONVERSATION` 记忆，在会话 A 里召回**只能看到 A 的那条**。
2. **上限生效**：把 `recall_limit` 设成 2，注入的记忆段里最多出现 2 条。
3. **降级生效**：把 `cv_memory_setting` 那一行删掉，对话仍能正常完成，日志里有 WARN。
4. **反证**：把 `CONVERSATION` 的 `scope_id` 过滤去掉，判据 1 必须红。

## 七、做梦（夜间整理）

用户问"记忆有没有做梦的能力"。业界（Ken Huang 的 agent dream 综述、Google 的 sleep framework、Generative Agents 的 reflection）给的定义是一致的：**离线任务读杂乱状态、写回更干净的记忆**。本设计落成**五个动作**，放在一个后台任务里（执行时刻由库里的 `dream_cron` 在运行期决定，见本节末）：

| 动作 | 做什么 | 为什么不是"实时做" |
|---|---|---|
| **去重合并** | 同 `dedup_key` 的合并成一条，`hit_count` 累加 | 实时合并会让每轮对话都多一次写放大 |
| **冲突消解** | 同一主题两条 contradictory，让模型判保留哪条，旧的 `superseded_by = 新的 id` | 需要"看到全貌"才能判；实时时只有局部 |
| **提炼** | 多条具体（"他上个月问过 A"、"他上周问过 B"）→ 一条抽象（"他在跟进 A 项目"） | 同上 |
| **遗忘** | `importance < min_importance` 且 `hit_count = 0` 且 `updated_at` 早于 `forget_after_days` ⇒ 软删 | ★ 用 `hit_count` 而不是"时间"：**从没被用过**的记忆才是噪音 |
| **重算画像** | 用 persona/cross_session 记忆重算 `cv_user_profile` | 每轮重算成本高且画像会抖 |

★ **幂等**：做梦任务可以对同一份数据跑多次，结果一致（合并用 `dedup_key`、消解只处理 `superseded_by is null` 的、遗忘只处理满足条件且 `deleted_at is null` 的）。停机跨过的夜晚不需要补跑 —— 与触发器 0.7.3 的取舍一致（`ROADMAP §11.42.2`）。

★ **cron 用 Spring 的 6 段式**（`0 40 3 * * *`），不像应用触发那样只收 5 段 —— 做梦的编排者是应用本身，不需要"用户少写一段"那层简化。

★ **执行时刻的唯一权威 = 库里的 `cv_memory_setting.dream_cron`**（`MemoryDreamScheduler`）：应用就绪时注册一次，保存设定后按新表达式重排（`MemorySettingsChanged` 事件，事务提交之后）。`MemoryDreamJob` 上原本的 `@Scheduled` 已经摘掉 —— 它的 cron 在注册 bean 时求值，改库改不动它，正是"界面上改了、日志里没异常、计划没变"的那类静默失败。部署配置 `app.memory.dream-cron` 只剩"迁移 V101 的初值"这一个用途；保存路径上 `MemorySettingsView.checked()` 会解析 cron，看不懂的表达式直接 400。

## 八、人格化

"用户对话人格化"不是"给模型加一段人设"，而是三件具体的事：

1. **画像里存的是可核对的行为**（"偏好先结论后依据"而不是"他是个直接的人"）；
2. **注入方式是"提示"不是"命令"**（"这位用户偏好…"而不是"你必须先给结论"），因为偏好会变，模型该有判断空间；
3. **画像可被用户看到并改**（§九），否则它就是一个用户不知道、也改不了的黑箱。

## 十、不做的（明确写下，避免被读成遗漏）

| 不做 | 理由 |
|---|---|
| 记忆共享给别人 / 团队记忆 | 记忆天然私人；团队知识的正解是知识库，不是把记忆共享 |
| 用外部向量库（Milvus/Qdrant） | 撞"不加服务"；`pgvector` 已在用，量级也够 |
| 记忆的版本历史（每次修改都留一份） | 有 `source_message_ids` 与 `superseded_by` 够回溯；完整历史会让表无限膨胀 |
| 实时做梦 | 需要全貌，且成本高 |
| 跨用户的画像对齐 | 属数据合规范畴（`#85` PII 出站），不在 `#296` |
| 记忆参与密级过滤 | 记忆是"用户自己说过的话"，其密级由其内容决定而非知识库；这一条留给 `#85` 一起定 |
