# 07 · 角色与数据权限模型

> **本册回答一个当前无法回答的问题**：*什么样的权限，看什么样的数据。*
>
> 现状是：这个平台有**权限点**（13 个，全是操作），但没有**数据范围** —— 于是「能看知识库」
> 与「能看哪些知识库」是同一个权限点，后者根本表达不出来。

---

## 一、问题：所有人都在做建设工作

### 1.1 三条实测证据

| # | 事实 | 读数 |
|---|---|---|
| 1 | 权限点共 **13 个，全是"操作"（动词）** | `knowledge:view/create/manage` · `document:upload` · `segment:edit` · `hittest` · `assistant:view/edit/publish` · `model:manage` · `dashboard:view` · `feedback:handle` · `system:manage` |
| 2 | ★ **`knowledge:view` 是无参数的** | 它只能回答「能不能看知识库」，**回答不了「能看哪些知识库」** |
| 3 | **契约里归属/可见性字段命中 0** | `owner` / `creator` / `createdBy` / `visibility` / `scope` / `shared` / `sharedWith` / `tenant` / `orgId` / `department` 全无 |

### 1.2 后果（量化，不是感觉）

`USER`（普通用户）只挂了 **2 个权限点**，但它看到的导航是 **4 个模块**：

```
admin     工作台 · 问答 · 知识库 · 应用管理 · 提示词 · 模型管理 · 运营看板 · 反馈处理 · 系统管理
zhangyun  工作台 · 问答 · 知识库 · 应用管理 · 运营看板 · 反馈处理
liwei     工作台 · 问答 · 知识库 · 应用管理 · 提示词 · 运营看板
chenjun   工作台 · 问答 · 知识库 · 应用管理          ← 普通用户
```

其中 **`知识库` 与 `应用管理` 是全平台建设面**。所以普通用户进来看到的是
**「整个工地，只是按钮少几个」** —— 这就是「大家都还在做建设工作」的机制，
不是观感问题。

### 1.3 根因：丢了旧系统的第三层

旧系统是**三层权限**（`需求规格说明书/01` FR-01-05，`01:68-88`）：

```
菜单权限  →  能看到哪些菜单、能点哪些按钮      ← 新系统有（路由 meta.permission）
数据权限  →  能看到哪些数据范围                ← ★ 新系统丢了
接口权限  →  接口级校验                        ← 新系统有（权限点）
```

旧系统的数据权限靠**租户 + 行级隔离**实现（BR-01-06/07：所有业务数据带租户标识）。
新设计把多租户推到 V2.0（`系统设计方案/04:72`），**数据权限就跟着一起被推走了** ——
于是 MVP 是「全员可见」（`04:369`）。

★ **本册的立场：多租户可以推，数据权限不能推。** 两者正交 ——
前者是"组织之间看不见"，后者是"同组织内我的是我的"。
一个单组织内网部署里，普通用户看到别人的知识库与应用，同样是错的。

## 二、角色重定义：把「使用者」与「建设者」分开

当前 4 个角色里，**前三个是岗位**（管理员 / 知识运营 / 应用配置），第四个是
「权限更少的岗位」。**缺的是"消费者"这个身份** —— 没有任何一个角色被设计成
「来用东西的，不是来建东西的」。

### 2.1 五个角色 + 一个非登录主体

| 族 | 角色 | code | 一句话定位 |
|---|---|---|---|
| **消费者** | **使用者** | `USER` | 只用别人做好的：问答、看引用、反馈。**界面上不出现任何"建设"语汇** |
| | 外部访客 | —（非角色） | 免登录，只走公开链接。**不是角色**，是凭证身份 |
| **建设者** | **个人建设者** | `CREATOR` | ★**新增**。能建**自己的**知识库与**简单**应用，发布给自己或小范围用 |
| | 知识运营 | `KB_OPERATOR` | 全平台知识库与文档治理、命中测试、反馈处理 |
| | 应用配置 | `APP_CONFIG` | 全平台应用配置、发布、编排 |
| | 管理员 | `ADMIN` | 账号、角色、模型、系统参数 |

### 2.2 为什么要把「普通用户」拆成两个

使用者的诉求是 **「无脑用」** —— 他不需要知道什么是分段、什么是向量化，
更不需要看到「上传文档」这个按钮。而个人建设者的诉求是 **「我也能弄一个」** ——
他需要建库、传文档、配一个简单应用，但**不需要**（也不该）碰全平台的资源。

合成一个角色的结果就是现在这样：为了照顾第二类人，把第一类人也丢进建设面。
**这是两个不同的人，应该是两个角色。**

`CREATOR` 的上限刻意收窄，写在权限点上：

- **能建**：知识库（自己）、简单应用（自己）、自己的会话与反馈
- **不能**：模型管理、提示词管理、编排应用、发布校验的绕过、看别人的东西、
  系统管理、运营看板（看板是全平台口径，给运营与管理员）

## 三、数据范围：必须引入「范围」这个维度

**不能靠加权限点解决。** `knowledge:view` 无论加多少个前缀都表达不了
「自己的 / 被共享的 / 全平台的」三种集合关系 —— 那是**范围**，不是**动作**。

### 3.1 资源侧：归属 + 可见性（三类资源统一）

知识库、应用、会话（含反馈）三类**用户产出**的资源，都加同样的三个字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ownerId` | `string` | 创建者。**不可变**（转让是显式动作，不是改个字段） |
| `visibility` | `'private' \| 'shared' \| 'public'` | `private` 仅自己 · `shared` 指定人或角色可见 · `public` 全平台可见 |
| `grants?` | `Grant[]` | 仅 `shared` 时有效。**不要用 `{ userIds, roleCodes }` 那种最简形状** —— 「共享」的演化空间最大，见 **§8.1**（那里给出了 `Subject` / `Grant` / `OwnedResource` 三个类型，MVP 只填其中两种主体） |

★ **`public` 不等于免登录。** `public` 是"登录用户里人人可见"；
免登录只有公开凭证（`AccessCredential`）那一条链路。两者混淆会造成越权。

### 3.2 角色侧：数据范围（三档）

`Role` 加一个字段（当前只有 `permissions: string[]`，没有表达位）：

| `dataScope` | 集合 | 典型角色 |
|---|---|---|
| `own` | 只有自己创建的 | 个人建设者 |
| `shared` | 自己创建的 **+** 被共享给自己的 | 使用者 |
| `all` | 全平台 | 知识运营 / 应用配置 / 管理员 |

（三档是**预设档位**，不是唯一形状 —— "本部门""我参与的项目"这类范围一定会来，
逃生口见 **§8.3**：先加枚举值，真需要表达式时才实现解析器。）

**为什么保留 `own` 与 `shared` 两档**（而不是只留 `shared`）：
`own` 的语义是**个人沙箱** —— 我只管我建的，别人分享给我的我也不想看见。
两者在"个人专注"场景下是不同的东西，合成一档就再也分不出来了。

★★ **与"个人库"的关系（2026-10-13 定 · `07 §3.2` 与 `13 §11.2` 的权威划分，`#31`）** ——
两处表达的是**同一件事的两半，不是两份真相**：

| | 管什么 | 权威落点 |
|---|---|---|
| `DataScope.OWN`（本节） | ★ **"共用库这一域里，我能看见哪些行"** —— 它是**范围档位**，会随组织/项目维度继续长（§8.3 逃生口） | 本节 |
| **个人库**（`owner_id = 我` 且 `kind = PERSONAL` 的库） | ★ **"这一行属于哪个域"** —— 它是**资源形态**，不是可见性档位 | `13 §11.2` |

⇒ ★ 三条不再另行解释的口径：**① 个人库不出现在任何"库"列表 / 选择器 / 绑定面 / 分享面里**（只走「我的资料」+ 检索时的「加上我的资料」开关，即 `13 §11.4` 的**隐式档**）；
**② `DataScope` 三档只作用在域谓词的第一支**（共用库），个人库与会话临时由"它就是我的"直接兜住（`13 §11.3`）；
**③ 不要把个人库实现成"一张普通的库、只是 owner 是你"** —— 那样它会顺着库列表 / 绑定 / 分享三条链路自动长出去，而三条各自都不会报错。

### 3.3 可见性判定：全工程唯一一条

```
可见(资源, 我) =
     dataScope === 'all'
  || 资源.ownerId === 我
  || (资源.visibility === 'shared' && 我 ∈ 资源.sharedWith)
  || (资源.visibility === 'public' && 我持有 '<资源>:view' 权限点)
```

**三条硬规矩：**

1. **这条判定只在后端实现一次。** 列表查询、单条查询、写操作的**前置校验**三处都走它 ——
   写操作也要走，否则「看不见但能改」这种越权最难发现。
2. **前端的隐藏入口只是体验，不是安全边界。** 前端按 `dataScope` 少渲染几个模块，
   但**后端不认前端的渲染** —— 直接调接口必须被拒（这正是 `04` 验收项 A7 的口径）。
3. **不应答的语义要统一**：看不见的资源，单条查询一律返回 **404 而不是 403** ——
   403 等于告诉对方"这个 id 存在"。

> 界面上的同族先例：权限点清单住在系统管理，而「给角色挂权限点」在角色管理里。

| 资源 | USER | CREATOR | KB_OPERATOR | APP_CONFIG | ADMIN |

| 反馈 | 自己提交的 | 自己提交的 | `all` | 自己提交的 | `all` |
| 提示词配置 | 不可见 | 不可见 | 不可见 | `all` | `all` |
| 模型 | 不可见 | 不可见 | 不可见 | 只读 | `all` |

⚠️ **会话那一行需要拍板**（第四节）。

### 4.3 数据约束（引用与删除的完整性）

| 约束 | 规则 | 违反时 |
|---|---|---|
| 应用 → 知识库 | 应用只能绑定**对它可见**的知识库 | 保存时拒绝（不是发布时才拒） |
| 应用 → 模型 | 只能选**已加载成功**的模型（契约已有） | 发布校验拦下 |
| 删除知识库 | 被应用引用时**拒绝删除**，并列出引用方 | `409` + 可读原因 |
| 删除应用 | 有已发布版本时要求显式确认 | 需二次确认 |
| 会话 → 应用 | 会话挂在应用上；应用删除后会话**保留**（归因快照） | 保留即可，不做级联删 |
| 所有者变更 | 只能**显式转让**，且需 `ADMIN` 或原所有者发起 | 普通编辑不可改 `ownerId` |
| 个人建设者**离职/停用** | 其资源需可被 `ADMIN` 接管（不能变成孤儿） | 停用账号时提示接管入口 |

## 五、页面形态随之分化（这才是"感觉"的解法）

**只加数据范围还不够** —— 使用者看到的 `知识库` 页面如果还是那张"卡片列表 + 新建按钮"，
他还是站在工地里。**同一份数据，两种页面形态。**

| 角色 | 首页 | 导航 | 知识库页形态 | 应用页形态 |
|---|---|---|---|---|
| **USER** | **应用广场**（能用什么） | 问答 · 应用广场 · 我的反馈（**3 项**） | 不出现 | **应用广场**：卡片 + 「开始问答」，**无新建/配置/发布** |
| **CREATOR** | **我的工作台** | + **我的知识库** · **我的应用**（5 项） | **我的知识库**：自己的（可建可删） | **我的应用**：自己的简单应用（可建可发布） |
| KB_OPERATOR | 工作台 | + 知识库 · 命中测试 · 反馈处理 | 全平台知识库（含归属列） | 只读 |
| APP_CONFIG | 工作台 | + 应用管理 · 提示词 · 编排 | 只读 | 全平台应用（含类型切换） |
| ADMIN | 工作台 | + 模型 · 看板 · 系统管理 | 全平台 | 全平台 |

**两条判据（可直接当验收）：**

1. **`USER` 登录后，界面上不该出现任何一个"新建"按钮**，也不该出现
   「上传文档 / 切分 / 向量化 / 分段」这类**建设语汇**。
2. **`CREATOR` 登录后，不该看到任何"别人的"资源** —— 他的知识库列表里
   只有他自己建的（以及明确分享给他的）。

★ 这也顺带解决了「工作台指标条」的角色问题：现在的 4 项指标
（问答次数 / 活跃用户 / 满意度 / 待处理反馈）是**全平台口径**，
对 `USER` 与 `CREATOR` 没有意义 —— 他们的首页该是「我的」口径
（我的提问数 / 我的应用 / 我的待处理），或干脆换成**应用广场**。

## 六、契约差距与迁移路径（契约是冻结的）

**这是本册最需要注意的地方。** 前端契约已冻结（`ROADMAP.md`），
加 `ownerId` / `visibility` / `sharedWith` 属于**破坏性变更**。
但有一条低风险路径 —— **只加可选字段 + 后端先落地过滤**：

### 阶段 1 · 后端落地（前端零改动即可工作）

- 创建类 `POST` **由后端自动写** `ownerId = 当前用户`、`visibility = 'private'`
  ⇒ 契约**不需要新增请求字段**
- 列表类 `GET` **由后端按 `dataScope` 过滤** ⇒ 契约不需要新增请求字段
- 契约只**新增可选响应字段** `ownerId?: string` / `visibility?: string`，
  以及一个可选的查询参数 `mine?: boolean`
  ⇒ **前端不传、不读，也照常工作**（这是"冻结契约"下唯一安全的加法）

### 阶段 2 · 前端按 `dataScope` 分化

- `Role` 加可选字段 `dataScope?: 'own' | 'shared' | 'all'`
- 导航过滤从「只看权限点」改成「权限点 **且** 有该范围的资源形态」
- 知识库/应用页按角色切形态（`我的` vs `全平台`）

### 阶段 3 · 共享 UI 与转让

- `sharedWith` 的编辑界面、资源转让入口、管理员接管入口

★ **阶段 1 就能单独发布**：它把"越权可见"从架构上关掉，
而前端一行不改 —— 这也是本工程一贯的做法（契约先冻结、后端在被约束下实现）。

## 七、需要拍板的四件事

| # | 问题 | 备选 |
|---|---|---|
| 1 | **管理员能不能看别人的会话？** | (a) **不能**（会话是私人对话，管理员只看聚合指标）· (b) 能，但需留痕 · (c) 能，用于质检 |
| 2 | **`CREATOR` 能不能建编排应用？** | (a) **不能**（编排是专业能力，归 `APP_CONFIG`）· (b) 能，但限节点数 · (c) 能 |
| 3 | **`public` 可见性要不要在 MVP 就有？** | (a) **MVP 只做 `private`**，`shared`/`public` 留 V0.2 · (b) 三档一起 |
| 4 | **新建知识的默认可见性** | (a) **`private`**（安全默认，要共享得显式动作）· (b) `shared` 全组织可见 |

> 建议：**1(a) · 2(a) · 3(a) · 4(a)** —— 四条都是"默认收窄、要放开得显式动作"。
> 理由：数据权限这种东西，**放开容易、收回难**（一旦有人习惯了能看全部，再收就是"功能退化"）。
> 反过来先收窄，需要时再放开，是一次纯增益的变更。

## 八、扩展口径（为后续留的口）

> 原话是：*「现在想不到那么多，但最好可以有扩展的空间。」*
>
> **这一节不是"把将来的功能都设计了"，而是把将来会长的地方换成"能长的形状"。**
> 每一条都只是**改变字段的表示**，**不增加当前工作量** —— 这是它与"过度设计"的分界线。
> §8.8 明确列出**不做**的那些，正是为了守住这条线。

### 8.1 ★ 最大的一个口：用 `grants` 表达共享，而不是 `{ userIds, roleCodes }`

最简形状是 `sharedWith: { userIds: string[]; roleCodes: string[] }`。它只够表达
"共享给这几个人和这几个角色"。而**「共享」这个概念的演化空间是全模型里最大的** ——
迟早要加：共享给部门、只读 vs 可编辑、有效期、可再分享、链接共享。

所以字段就**取那个能长的形状**（MVP 只填 `user`/`role` 两种主体、每类资源一个动作）：

```ts
type SubjectKind = 'user' | 'role' | 'org' | 'group' | 'link'
interface Subject { kind: SubjectKind; id: string }

interface Grant {
  subject: Subject
  actions: string[]           // 与权限点同一套词汇：knowledge:view / assistant:edit …
  expiresAt?: string | null   // 时效
  canDelegate?: boolean       // 可再分享
}

interface OwnedResource {
  ownerId: string
  visibility: 'private' | 'shared' | 'public'
  grants?: Grant[]
}
```

**加"共享给部门" = 加一个 `SubjectKind`；加"只读/可编辑" = 每条 grant 多一个 action；
加"有效期" = 填 `expiresAt`。** 三种扩展都**不动判定函数、不动表结构、不动契约形状**。

★ 反面做法是把 `sharedWith` 写成两个数组 —— 那时上面三种扩展每一种都要**改字段**，
而字段一改，前端、后端、数据库一起动。**这是本册成本最低、收益最高的一处形状选择。**

### 8.2 判定接收「主体集合」，不接收「当前用户」

```
可见(资源, 主体集合 S) =
     scope(角色) === 'all'
  || 资源.ownerId ∈ S.ids
  || ∃ g ∈ 资源.grants: g.subject ∈ S 且 动作 ∈ g.actions
  || (资源.visibility === 'public' 且 动作 ∈ 主体权限点)
```

`S` = `{ 该用户, 其角色, 其部门, 其项目组, … }`。现在只填**用户与角色**两项；
将来加"部门""项目组"只是**往集合里多塞一项** —— 判定本身一个字不改。

★ 这也是**外部协作者**的接入点：外部人也是主体，只是来源不同。

### 8.3 `dataScope` 是**预设档位**，不是唯一形状

`own | shared | all` 覆盖现在能想到的全部。但"本部门""本部门及下级""我参与的项目"
这类需求一定会来。所以：**枚举保留为预设档，同时留一个规则字符串的口子**：

```ts
dataScope: 'own' | 'shared' | 'all'   // 预设档，覆盖绝大多数场景
dataScopeRule?: string                // 逃生口：结构化规则（先不做解析器）
```

MVP **只实现枚举**，`dataScopeRule` 留空且不读。将来加"本部门"时的正解是
**先加一个枚举值 `'org'`** —— 大多数情况下这就够了；真需要表达式时才去实现解析器。

### 8.4 归属与判定做成**可复用形状**，不要每类资源写一遍

现在三类资源（知识库 / 应用 / 会话）。将来还有文档、分段、提示词、数据集…
所以：**后端一个 `OwnedResource` 接口 + 一个判定入口；前端一个 `ResourcePolicy` 类型。**
加一类资源 = 实现同一个接口，**判定逻辑零复制**。

★ 判据：**如果加第四类资源时你需要复制判定函数，说明形状选错了。**

### 8.5 判定必须**可下推为 SQL 谓词**（性能口）

```sql
WHERE owner_id = :me
   OR visibility = 'public'
   OR EXISTS (SELECT 1 FROM grants g
               WHERE g.resource_id = r.id
                 AND g.subject IN (:subjects)
                 AND :action = ANY(g.actions))
```

**不许"取全量再在内存里过滤"** —— 那是把权限做成 O(n)，
数据量一上来要么慢、要么被人绕过分页。这一条是**实现约束**，
但必须现在写下来：**等到列表分页之后再改，就要动查询结构。**

### 8.6 与多租户**正交**，表达为可组合谓词

```
可见 = 租户内(资源) AND 范围匹配(资源, S)
```

将来开多租户只是**与**上一个条件（`AND tenant_id = :t`），范围逻辑一个字不改。
这正是 §一 里"多租户可以推、数据权限不能推"的结构化表述 —— **两者是可乘的，不是二选一。**

### 8.6.1 ★ 密级：第三个正交维度（`13` 册）

```
可见 = 租户内(资源) AND 范围匹配(资源, S) AND 密级(资源) ≤ 我的上限
```

★ **密级与 `dataScope` 正交**：范围回答"**谁的**"，密级回答"**多敏感**" ——
一份"我自己的"文档可以是**机密**，一份"全平台可见"的文档可以是**公开**。
**把两者混成一个字段，会出现"因为是我建的所以能看机密"这种荒谬结论。**

⇒ 完整设计（等级 + 标签的模型 · 传播与漂移 · **五道闸门** · RLS × HNSW 的坑 ·
引用与分享隔离 · 审计 · **P0→P3 落地分期**）见 **`13-密级与数据隔离设计.md`**。

★ **与本册的关系**：它是同一个"**可组合谓词**"思路的第二个使用者 ——
判定入口**仍然是唯一的**（§8.7），只是那个入口现在要同时管"归属范围"与"密级上限"两个条件。

### 8.7 判定**单一入口**，为了将来能挂审计

"谁看了谁的数据""谁把资源分享给了谁"，这类问题上线后一定会被问。
判定只有一个入口，**审计就只有一个挂载点**。

★ 这也是 §3.3「只在后端一处实现」的**第二个理由**：
第一个理由是安全（避免漏一处就漏一处洞），第二个理由是**可观测**。

### 8.8 明确**不做**的（防过度设计）

| 不预留 | 理由 |
|---|---|
| 规则表达式的**解析器** | 先加枚举值通常就够（8.3）；真需要时再实现 |
| 角色的继承链 / 角色树 | 现在角色是平的，加继承要动判定顺序 —— 「要了再说」 |
| ABAC / 属性策略引擎 | 属性来源（部门、项目）本身都还不存在，先做等于空转 |
| 资源内的**字段级**权限（同一行不同字段可见性） | 复杂度极高，且与"整行可见性"是两个不同的问题 |
| 跨组织的委派 | 与多租户同批（V2.0） |

★ **8.1–8.7 与这五条的区别**：前者是**换形状**（零额外工作量，现在就该做）；
后者是**加机制**（有成本，等有需求再做）。**只做前者。**

## 十、组织机构树（★ 数据权限的载体，第 19 周前的形状收口）

### 10.1 为什么它现在就要落形状

今天"责任部门"是 `kb_document.department varchar(64)` 上的**一个自由字符串**，前端只给建议值
（`DEPARTMENT_SUGGESTIONS`）。这有三个后果：

1. **它进召回前缀**（`12 §4.2`：`search_text = 文种|部门|标题|路径|正文`），所以它不是一个纯展示字段；
2. **它进 `content_hash`**（`SEG-I7`）⇒ 改部门名会让该部门下所有文档"前缀变了 ⇒ 需要重新向量化"；
3. ★ **它没法做数据权限**：字符串比不出"我的部门 + 下级"，也没法作为共享主体。

⇒ 数据权限（`§五/§六`）要真正按组织隔离，**必须先把部门实体化**：
`department` 字符串 → `kb_document.org_id`（外键）。★ 这属于 `13 §8.2` 那条判据
（"会进 SQL 谓词或改数据形状"）⇒ **必须在库里还没量产数据时改**，晚了就是回填 + 全量巡检。

### 10.2 `iam_org` 的形状：物化路径，不用递归 CTE

| 列 | 说明 |
|---|---|
| `id` / `code` | `code` 是**稳定的机器码**（进 grants 的 `subject_id`，也进 JWT/审计），改名不改码 |
| `parent_id` | 自引用；根节点的父为 null |
| `path` | ★ **物化路径**（形如 `/root/procurement/`），"含下级"= `path like :prefix \|\| '%'` |
| `sort` / `enabled` | 排序与启停（停用的部门不参与新的共享，但**不影响既有数据**） |
| `name` | 展示名。★ **改名会让前缀变 ⇒ 该部门下文档需要重新向量化**（§10.1 第 2 条），要提示 |

★ 为什么用物化路径而不是递归 CTE：**数据权限要在每一条检索 SQL 里生效**（`13 §三` 的 pre-filter），
而"我的部门及下级"在物化路径下是一个**字符串前缀比较**，planner 能用上索引；
递归 CTE 放进每一条检索查询，既难读又难被 planner 优化。代价是**移动部门要重写子树路径**
（一次 `update ... where path like ...`），而移动是低频操作。

### 10.3 与既有两套机制的关系（★ 别再出现"同一件事两处真相"）

| 机制 | 管什么 | 与组织树的关系 |
|---|---|---|
| `DataScope`（`ALL/SHARED/OWN`，进令牌） | **账号级**：这个人默认看多大范围 | ★ **本版不加档**（见下） |
| `kb_knowledge_base_grant`（`subject_kind` ∈ USER/ROLE/**ORG**） | **资源级**：某条资源额外共享给谁 | ★ 组织树的**第一个消费者**：`ORG` 分支按 `path` 前缀判"含下级" |
| `ScopeFilter.canSee` | 上面两者的**唯一**判定点（`§3.3` 硬规矩 1） | 加 `ORG` 分支时**只改这一处** |

★ **本版不给 `DataScope` 加"部门档"**，理由：那三档是**账号级**的，加档要同时动
令牌声明、仓储的 `search(scope,…)`、前端 `scopeForms` 三处；而"共享给部门"用**现成的 grant 机制**
就能表达（`SubjectKind.ORG` 早已预留）。等到出现"新文档自动对本部门可见"这类**非显式共享**的需求，
再加档——那时也只需要在 `ScopeFilter` 一处加分支。

### 10.4 用户归属

`iam_user.org_id`（可空：还没来得及归类的账号）。★ **一人一部门**（MVP）：
多部门归属会让"我的部门及下级"变成集合运算，而共享主体（grant）本身就已经是集合语义了 ——
如果将来真要一人多部门，正确的做法是加一张 `iam_user_org`，**不是**把 `org_id` 改成数组。

### 10.5 判据

1. 把一条知识库共享给某部门 ⇒ 该部门的人（**含下级**）看得见；**别的部门的人看不见**（含兄弟部门）。
2. 移动一个部门到别处 ⇒ 它的下级跟着走（`path` 前缀重写），**共享关系不失效**。
3. 停用一个部门 ⇒ 不产生新的共享，**既有共享不变成不可见**（停用 ≠ 撤销）。
4. ★ 金丝雀：把 `ScopeFilter` 里 `ORG` 分支的"含下级"改成"精确匹配" ⇒ 判据 1 必须变红。

## 十一、组织机构的三个消费位（★ 用户 2026-10-08 指出「责任部门没接到组织机构 / 知识库适用范围没在组织机构归属下」）

> 形状已经落好了（`§十`），但**一个"载体"落完不等于它被消费了**。本节回答"组织机构到底在哪些地方
> 真的起作用"，因为**它有三个语义不同的消费位**，而把三者混成一个正是最容易出的错。

### 11.1 三个位置，三种语义（★ 不要合并）

| # | 位置 | 语义 | 存什么 | 含下级？ | 谁判 |
|---|---|---|---|---|---|
| ① | 文档 `kb_document.org_id` | **归属**：这条文档是谁的 | 外键 → `iam_org.id` | ★ **否**（精确一个部门） | 展示 + 可选过滤 |
| ② | 知识库共享 `kb_knowledge_base_grant`（`subject_kind = ORG`） | **共享**：这个库给哪个部门看 | `subject_id` = 部门 id | ★ **是**（按 `path` 前缀） | `ScopeFilter.canSee` |
| ③ | 用户 `iam_user.org_id` | **身份**：这个人属于哪个部门 | 外键 → `iam_org.id` | ★ **是**，但**方向相反**：判定用的是"**我的部门及上级**"这条祖先链（见 §11.3 的方向说明） | `ScopeFilter` 的授权基 |

★★ **① 与 ② 不是同一件事**，这是本节最该记住的一句：

- **「文档归属 A 部门」≠「A 部门的人都能看这篇文档」。** 文档能不能被看见由**库的共享**（②）决定；
  ①只回答"这条文档属于谁"（展示、审计、以及将来可能的更细过滤）。
  ⇒ ★ **推论（防过度设计）：`org_id` 不进检索的可见性谓词。** 谁把"归属"当成"可见性"，
  就等于把"责任部门"偷偷改名成"访问控制列" —— 而这两件事的**判定时点完全不同**
  （归属是建档时写一次的事实；可见性是每次检索逐行算的谓词）。
- **「含下级」只属于 ② 与 ③，不属于 ①。** 共享给"技术部"含义是"技术部及下级都看得见"（用户口径）；
  而一篇文档的归属就是**一个**部门，说"这篇文档归属技术部及其下级"没有意义。
  ⇒ ★ **两处口径必须分开写，且各写一次** —— 本项目对"同一条链上两处同语义的网"极敏感
  （第 11 周密级 pre-filter 的教训：两道同语义的网会让端到端断言分不清谁在起作用）。

### 11.2 文档归属落地（对应 `T300`）

**形状**：`kb_document.department`（varchar 自由串，前端只给建议值）→ **`org_id`（外键）**。
今天它同时 (a) 进召回前缀 (b) 进 `content_hash` (c) 没法做数据权限 —— 字符串比不出"我的部门+下级"。

**建档**：责任部门从**自由输入/建议值**改成**组织树选择**，默认带出**上传者自己的部门**
（`iam_user.org_id`），允许改（跨部门代传是真实场景）。

**★ 前缀与 `content_hash` 去名字化 —— 用稳定 `code`，不用 `name`、也不用 `path`：**

| 放什么 | 改名 | 移动部门 | 重名 | 结论 |
|---|---|---|---|---|
| `name`（今天的做法） | ★ **整部门文档向量全废** | 无影响 | ★ 有歧义（可重名） | ❌ |
| `path` | 无影响 | ★ **整棵子树的向量全废** | 无歧义 | ❌ |
| **`code`** | 无影响 | 无影响 | 无歧义（全局唯一且不可改） | ✅ |

★ 因为 `code` 是**身份**（不可改）、`name` 只是**表达**（可改、可重名）：可变的东西不配进入身份判定，
更不该进入向量与哈希的材料。人读的部门名改在**生成链路渲染时**由 `org_id` 查出来
（与密级/文种走字典渲染是同一套模式）。

**回填**：按 `name` 匹配现有 `department` 字符串 → `org_id`。
★ **匹配不上的（自由输入的自造部门/错字）不许猜**：原值留在 `department_legacy` 存档列、
`org_id` 置空，并由一条**巡检**把它们列出来 ⇒ 不静默丢信息、也不静默认领。

### 11.3 知识库适用范围落地（对应 `T301`）

**形状**：复用现成的 `kb_knowledge_base_grant`（`SubjectKind.ORG` **早已在契约里预留**，
但至今零消费方 —— 典型的"契约里有这个主体类型 ≠ 有人用它"）。共享对话框新增「部门」主体 + 树选择。

**判定**：`ScopeFilter` 的 grants 加 `ORG` 分支 —— "我的部门及上级"一次 SQL 取 id 集合
（`select id from iam_org where :myPath like path || '%'`），再 `grant.subject_id in (…)`。★ **只改 `ScopeFilter` 这一处**（`§3.3` 硬规矩 1）。

> ### ★★ 方向（`T301` 落地时对出来的，**这是本节最容易写反的一处**）
>
> 判定写的是 `我的集合.contains(共享目标)`，而共享给「技术部」的含义是「**技术部及下级**都看得见」。
> "我在技术部的下级里"换个说法就是"**技术部在我的祖先链上**" ⇒ 集合必须是**祖先链**（我的部门 + 它的全部上级）。
>
> 取成子树（"我的部门 + 下级"）得到的是**镜像语义**："共享给我的**下级**部门 ⇒ 我看得见" —— 那不是任何一条产品承诺，
> 而且会让上级自动看见下级的共享。两个方向都能跑、都不报错、症状恰好相反，所以：
> **口径写在这里一次，方向写进方法名（`OrgDirectoryPort.ancestorsAndSelf`），金丝雀守在 `ScopeFilterTest`
> 与 `AccessScopeOrgScopeTest` + `OrgScopeWiringTest` 三处**。
>
> ⚠️ 本节原先那句"我的部门及下级"就是这个镜像说法（`§11.1` 表格的 ③ 行同样），已订正 —— 术语用反了，
> 照它实现出来的是"上级看下级的共享"。

**★ 粒度是「库」，不是「文档」**：共享给 A 部门（含下级）= 能看到该库的**全部文档**。
"同一个库里只能看到本部门的文档"（文档级过滤）**明确不做** —— 那需要**另一条谓词**，
而且会让"共享了这个库、却只看得见一半"变成难以解释的行为。真出现这种需求时单独立项。

### 11.4 判据（可核对，写不出读数就说明还没想清）

1. **移动部门 ⇒ 不需要重新向量化。** 一条单测钉住：改 `name` / 移动（改 `path`）/ 改 `sort`
   ⇒ 该部门下文档的 `content_hash` 与既有向量**逐字节不变**。
   ★ 这条同时是"前缀里不许出现 `name`/`path`"的哨兵 —— 谁哪天把 `path` 塞进前缀，它立刻红。
2. **改名 ⇒ 不需要重新向量化**（同上一条的两个方向）。
3. **`kb_document.org_id` 为空的条数 = 0**（除回填时列进"未匹配清单"的那些）。
4. **共享给某部门 ⇒ 该部门（含下级）看得见，兄弟部门看不见**（`§10.5` 判据 1 的复用）。
5. ★ 金丝雀（a）：`ORG` 分支的"含下级"改成"精确匹配" ⇒ 判据 4 变红。
6. ★ 金丝雀（b）：把前缀里的 `code` 换回 `name`，然后改一个部门的名字 ⇒ **判据 1 变红**。
   （守的是"可变展示名不许进向量材料"这条不变量。）

### 11.5 交付顺序（为什么 `T300` 必须早）

`T300`（形状 + 回填 + 前缀去名字化）→ `T301`（谓词 + 金丝雀）→ `T302`（前端三处：建档责任部门 /
知识库共享主体 / 用户归属部门）→ `T303`（收口：两条真栈闸门 + `mvn verify` + 文档 + `CHANGELOG`）。

★ 理由同 `§10.1`：`department → org_id` 是**改数据形状**，越晚做越贵（既有数据要回填一次，
而回填按名字匹配的准确率只会随时间下降）。**其余三项都是在它之上加消费方，不返工。**

## 十二、源系统 ACL 的映射口径（★ 留缝：权限的**权威源**，issue `#81`）

> **为什么单开一节**：本册以上全部内容都假定"权限是平台内标注的" —— `dataScope` · 归属 · 可见性 · grants ·
> 密级，**没有一处回答"知识从哪来"**。而企业里已有的知识在 SharePoint / Confluence / 网盘 / 共享目录 / 企业 IM 里，
> 那些系统**各自有权限**。口径不先定，做连接器时**每条导入路径都要重新想一次权限映射**（`#81` 危害 ②）。
>
> ★ **本节只定口径与字段位置，不实现**（`ROADMAP §11.7.1`：`§二` 清单里没有它 ⇒ 本该只记账；
> 但它满足"现在不做会返工" ⇒ **留缝**）。实现（连接器 / 增量同步 / ACL 拉取）全部排在 `0.5.x` 之后。

### 12.1 结论：**平台内标注是唯一权威源**；源系统 ACL **不参与判定**

★ 一句口径（**冲突时谁赢，见 12.3**）：

> **可见性判定读的只有平台内那一个谓词**（`§3.3` 的 `ScopeFilter` + `13 §三` 的 pre-filter）。
> 源系统的 ACL 是**导入时的输入**，不是检索时的判据 —— 它必须先被映射成平台内的密级 / 组织 / grant，
> **然后**才起作用。今天这个映射**不存在**。

### 12.2 映射方向（未来实现时的形状，现在只写下来）

| 源系统的东西 | 映射到平台内哪个东西 | 为什么是它 |
|---|---|---|
| 源文档的**可见范围**（站点/库/文件夹/文档四级 ACL） | **知识库的 `kb_knowledge_base_grant`（`SubjectKind.ORG/USER/ROLE`）** | ★ 本册 `§11.3` 已定：**粒度是「库」，不是「文档」**。文档级过滤目前明确不做（那需要**另一条谓词**） |
| 源文档的**敏感度标签**（Purview / 密级字段） | **`kb_document.classification` + `labels`**（`13 §1`） | 只有它进 `13 §三` 的 pre-filter；映射到别处等于过滤不生效 |
| 源文档的**责任部门** | **`kb_document.org_id`**（外键，`§11.2`） | 归属的语义就是"这条文档是谁的"，与 ACL 不同（`§11.1` ★★ 已写死） |
| 源系统的**账号 / 组** | **`iam_user` / `iam_org` / `Role`**（见 `§十三`） | 主体必须先在本平台存在，否则 grant 无从表达 |

★ **反向不成立**：平台内的密级变更**不写回**源系统（单向）。理由：写回需要源系统的写权限与冲突解决协议，
而那是另一个量级的工程；且"平台把源系统的密级改了"会让源系统的合规状态失真。

### 12.3 ★★ 冲突时谁赢（本节的硬要求）

| # | 冲突 | 谁赢 | 为什么 |
|---|---|---|---|
| 1 | **源 ACL 比平台密级更宽**（源说"人人可见"，平台标了 `机密`） | ★ **平台密级赢，严格不可放宽** | 密级是**单向不可逆**的（`13 §2.1`）。让源系统放宽平台密级 = 一句"我们按源系统的权限走"就把 `13 §三` 的五道闸门作废 |
| 2 | **源 ACL 比平台密级更窄**（源只给一个组看，平台标了 `公开`） | ★ **以源 ACL 映射出来的 grant 为准**（即**取交**方向） | 这一侧收窄是安全的，而且它正是"继承企业既有权限"的价值所在 —— 但★**这是未来实现时的方向，今天不生效**（今天根本没有源 ACL） |
| 3 | **源系统说 A 部门，平台内 `org_id` 说 B 部门** | **平台内 `org_id` 赢**（它进审计与展示）；差异记进**巡检读数**，不静默改 | 同 `§11.2` 对"回填匹配不上"的处置：**不静默丢、不静猜测**（本项目已栽过的形状） |
| 4 | **源系统的密级标注与平台标签不一致** | **平台标签赢**；两侧都记进审计 | 审计要能回答"当时判定依据是什么"（`13 §7.1`）—— 只留赢的一方，事后复盘就少了一半证据 |
| 5 | **源 ACL 引用与平台权限点冲突**（源说能看，但用户没有 `VIEW` 权限点） | ★ **平台权限点赢** | 功能权限与数据权限是**两条轴**（`§4.1` vs `§4.2`）。源 ACL 表达的是"数据可见性"，它**不能**替用户拿到一个功能权限 |

★ **第 1 条与第 5 条方向相反不是矛盾**：**"能做什么"以平台为准，"能看哪些"取交**。
把它们写成一句话（"以源系统为准"或"以平台为准"）都会在某一侧出错 —— 这正是本节必须逐条写的原因。

### 12.4 位置（★ 只留位置，不建表、不实现）

`kb_document` 上未来要有的四列（**今天一个都不存在**）：

| 列 | 类型 | 语义 |
|---|---|---|
| `source_doc_id` | `varchar(256)` | 源系统里的**稳定文档标识**（用于增量同步与"同一份文档的再次同步"） |
| `source_revision` | `varchar(64)` | 源系统的**版本/修订标识**（用于判断"源端更新了没有"；★ 与 `#86` 的文档版本是**两件事**，见 `12 §9.3`） |
| `source_acl_ref` | `varchar(512)` | 源 ACL 的**引用**（一个可重放的句柄：源站点/库/项 id 的组合），**不是**权限本身 |
| `source_synced_at` | `timestamptz` | 上次从源同步的时刻（做"源端改了、平台还没跟上"的读数用） |

★ **`source` 这一列已经存在**（`knowledge/domain/Document.java` 的 `source` / 契约 `DocumentItem.source`），
但它是**来源渠道**串（今天恒为 `local`），**不是权限依据** —— 不要把这两件事混成一件（`#81` 容易犯的错）。

### 12.5 ★ 与既有的 `source` 字段划清界限（★ 防重复记账）

| 已有的东西 | 管什么 | 是不是"权限的权威源" |
|---|---|---|
| `kb_document.source`（`varchar(32)`，今天恒 `local`） | **来源渠道**（本地 / 在线），做展示与统计 | ❌ 不是 |
| `import_type`（知识库上，`LOCAL` / `ONLINE`） | **这个库怎么进料** | ❌ 不是 |
| `ScopeFilter` / grants / 密级 | ★ **能看见什么** | ✅ **唯一的权威源** |

⇒ 本节补的是**第四件**：源系统的权限**怎么进来**、**冲突时谁赢**。它不是在已有的三件上加装饰。

### 12.6 为什么现在不做（口径写在前面，实现排在后面）

| # | 理由 |
|---|---|
| 1 | **源 ACL 没有落点可映射**：它必须先映射成"库的共享"或"文档的密级"，而"文档级过滤"在 `§11.3` 里**明确不做** ⇒ 实现它等于先推翻那条粒度决策 |
| 2 | **没有源系统可接**：本仓对"连接器 / 增量同步 / SharePoint / Confluence"**零命中**（`#81` 依据表）—— 没有需求时实现它 = 写无人使用的代码 |
| 3 | ★ **但位置与"谁赢"必须先定**：晚定就要改已经写好的导入路径与谓词（`13 §8.2` 的判据）⇒ 这正是"留缝"的适用面 |

### 12.7 触发条件（什么时候这条缝要变成实体）

**任一成立**即立项：

1. 出现**要接的源系统**（SharePoint / Confluence / 网盘 / 共享目录 / 企业 IM 之一）；
2. 出现**已复现的越权案例**：某用户在平台搜到了"他在源系统看不到"的段落；
3. `§11.3` 的"文档级过滤**明确不做**"这条决策被推翻（那意味着粒度变了，本节要跟着重写）。

### 12.8 ★ 判据（留缝做完算什么）

1. ✅ 本节存在，且 **12.3 逐条写了"冲突时谁赢"**（不能只写"参考源系统"）；
2. ✅ 字段位置在 12.4（**只写名字与类型，不建表**）；
3. ★ **一条能红的断言**：`SourceAclAuthorityAbsenceTest.assertSourceAclSyncIsNotImplemented`
   （`backend/src/test/java/cn/lincoln/aiplatform/caliber/`）—— 它断言
   **`kb_document` 的字段与列清单里没有任何"源系统授权依据"**，且 `ScopeFilter` 的输入里一个源系统维度都没有。
   谁把 `source_acl_ref` 之类的列加进来（或让 `ScopeFilter` 开始吃源 ACL），它就**立刻变红**，
   逼人回到 12.3 回答"冲突时谁赢"。

## 十三、组织与账号的权威源（★ 留缝：目录同步，issue `#82`）

> **为什么单开一节**：`§十`/`§十一` 把组织树的**形状**与**三个消费位**定得很细，但**没有一处回答"这棵树是谁维护的、它凭什么是对的"**。
> 而部门数据权限的正确性**完全依赖组织树是准的** —— 树一歪，"共享给技术部"就把库给错了人（`#82` 危害 ①）。

### 13.1 结论：**组织与账号的权威源是平台内**（`iam_org` / `iam_user`，管理员维护）

今天只有一条路径：人在平台里建部门、建账号、改归属。**没有任何外部同步源**。

### 13.2 ★ 与 SSO 的区别（★ 本节存在的主要理由）

| 概念 | 回答的问题 | 本项目的状态 |
|---|---|---|
| **SSO**（单点登录） | **怎么登录**（凭据从哪来、要不要跳转） | `04:79` · `03:570` 定为「**按需**推迟」（内网账号密码足够）—— ★ **这个判断今天仍然成立** |
| ★ **目录同步**（AD / LDAP / SCIM） | **有哪些人、谁在哪个部门、谁离职了** | ★ **零命中**（全 `docs/` 对 `LDAP｜SCIM｜目录服务｜AD 域` 无业务命中） |

> ★★ **把两者当一件事，就会得出"SSO 推迟了 ⇒ 组织是平台内的也没问题"这个错误结论**（`#82` 的根因）。
> SSO 是**登录方式**，目录同步是**权限模型的输入**。前者可以推，后者的**口径**不能推
> —— 因为 `§十一` 的三个消费位已经建在组织树上了。

`需求规格说明书/01:47` 的 `FR-01-03-4` 单点登录（授权码模式）**只覆盖前者**，它不解决"人从哪来"。

### 13.3 ★ 冲突时谁赢（本节的硬要求）

| # | 冲突 | 谁赢 | 为什么 |
|---|---|---|---|
| 1 | **平台内手工改过的组织 vs 目录里的组织** | ★ **平台内赢**，且**不写回**目录 | 同 `12.2` 的反向不成立：写回要源系统的写权限与冲突解决协议，是另一个量级的工程；而"平台把目录改了"会让目录的合规状态失真 |
| 2 | **人离职 / 停用** | ★ **平台内立刻收敛**：`iam_user.status = DISABLED`（**不是**删行 —— 它是审计字段 `created_by/updated_by` 指向的东西，`User` 的类注释已写死） | 离职后权限不收敛正是等保对"访问控制"的检查点（`#82` 危害 ③） |
| 3 | **人调岗** | ★ **以平台内 `iam_user.org_id` 为准**；目录同步只做**建议值**，不静默覆盖 | 手工归属承载了"借调 / 兼岗 / 过渡期"这些目录表达不了的事实；静默覆盖会把它们抹掉而**不报错** |
| 4 | **目录里删了一个部门，平台内还有它的文档 `org_id`** | ★ **不级联删**：部门**停用**（`enabled=false`），既有共享**不失效** | `§10.5` 判据 3 已写死「停用 ≠ 撤销」。级联删会让历史文档的归属变成空指针 |
| 5 | **目录与平台内的 `code` 冲突**（同名不同人 / 不同节点） | ★ **平台内 `code` 赢**；外部标识另存（见 13.4），**不与 `code` 合并** | `§十` 已写死：`code` 是**身份**（不可改、全局唯一），`name` 只是表达。把外部 id 塞进 `code` 等于让一个可变的系统来源成为身份的一部分 |

★ **共同的规律**：**平台内永远赢"改什么"，目录只赢"提供候选"**。理由不是偏好 —— 是"平台内的改动承载着目录表达不了的事实"（借调、过渡、审计要求）。

### 13.4 位置（★ 只留位置，不建表、不实现）

| 表 | 列 | 类型 | 语义 |
|---|---|---|---|
| `iam_org` | `external_id` | `varchar(256)` | 该节点在**目录服务**里的标识（DN / objectGUID / SCIM id） |
| `iam_org` | `directory_source` | `varchar(32)` | 来自哪个目录（`AD` / `LDAP` / `SCIM` / `MANUAL`） |
| `iam_user` | `external_id` | `varchar(256)` | 该账号在目录里的标识 |
| `iam_user` | `directory_source` | `varchar(32)` | 同上 |
| （未来） | `directory_synced_at` | `timestamptz` | 上次同步时刻（做"目录改了、平台还没跟上"的读数用） |

★ **`iam_org.code` 不是 `external_id`**：前者是**平台内的身份**（进 grants 的 `subject_id` 与审计），
后者是"这个节点在 AD 里是谁"。**合并它们会让身份跟着目录变**（`§十` 的 `code` 契约会被破坏）。

### 13.5 为什么现在不做

| 1 | **没有目录可接**：`docs/` 对 LDAP / SCIM / AD 零命中 ⇒ 没有需求时实现它 = 写无人使用的代码 |

| 3 | **SSO 的推迟不改变这一条**：见 13.2 —— 两者是不同的问题 |

### 13.6 触发条件

**任一成立**即立项：

1. 出现**要接的目录服务**（AD / LDAP / Entra ID / SCIM）；
2. 出现**已复现的权限错判**，且根因是"组织树与真实组织脱节"；
3. 审计要求"**访问权限随人事变动自动收敛**"（等保检查项）成为硬约束。

### 13.7 ★ 判据（留缝做完算什么）

   `OrgService` 的公开入口里**没有"把一份目录快照整体应用进来"这类能力**。
   谁加了 `external_id` / `directory_source`（或给 `OrgService` 加了一个批量 apply 入口），它就**立刻变红**。

| 既有处 | 管什么 | 与本节的关系 |
