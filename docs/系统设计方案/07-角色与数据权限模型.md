# 07 · 角色与数据权限模型

> **本册回答一个当前无法回答的问题**：*什么样的权限，看什么样的数据。*
>
> 现状是：这个平台有**权限点**（13 个，全是操作），但没有**数据范围** —— 于是「能看知识库」
> 与「能看哪些知识库」是同一个权限点，后者根本表达不出来。

---

## 一、问题：所有人都在做建设工作

### 1.1 三条实测证据

| # | 事实 | 读数 |
|---|---|---|
| 1 | 权限点共 **13 个，全是"操作"（动词）** | `knowledge:view/create/manage` · `document:upload` · `segment:edit` · `hittest` · `assistant:view/edit/publish` · `model:manage` · `dashboard:view` · `feedback:handle` · `system:manage` |
| 2 | ★ **`knowledge:view` 是无参数的** | 它只能回答「能不能看知识库」，**回答不了「能看哪些知识库」** |
| 3 | **契约里归属/可见性字段命中 0** | `owner` / `creator` / `createdBy` / `visibility` / `scope` / `shared` / `sharedWith` / `tenant` / `orgId` / `department` 全无 |

### 1.2 后果（量化，不是感觉）

`USER`（普通用户）只挂了 **2 个权限点**，但它看到的导航是 **4 个模块**：

```
admin     工作台 · 问答 · 知识库 · 应用管理 · 提示词 · 模型管理 · 运营看板 · 反馈处理 · 系统管理
zhangyun  工作台 · 问答 · 知识库 · 应用管理 · 运营看板 · 反馈处理
liwei     工作台 · 问答 · 知识库 · 应用管理 · 提示词 · 运营看板
chenjun   工作台 · 问答 · 知识库 · 应用管理          ← 普通用户
```

其中 **`知识库` 与 `应用管理` 是全平台建设面**。所以普通用户进来看到的是
**「整个工地，只是按钮少几个」** —— 这就是「大家都还在做建设工作」的机制，
不是观感问题。

### 1.3 根因：丢了旧系统的第三层

旧系统是**三层权限**（`需求规格说明书/01` FR-01-05，`01:68-88`）：

```
菜单权限  →  能看到哪些菜单、能点哪些按钮      ← 新系统有（路由 meta.permission）
数据权限  →  能看到哪些数据范围                ← ★ 新系统丢了
接口权限  →  接口级校验                        ← 新系统有（权限点）
```

旧系统的数据权限靠**租户 + 行级隔离**实现（BR-01-06/07：所有业务数据带租户标识）。
新设计把多租户推到 V2.0（`系统设计方案/04:72`），**数据权限就跟着一起被推走了** ——
于是 MVP 是「全员可见」（`04:369`）。

★ **本册的立场：多租户可以推，数据权限不能推。** 两者正交 ——
前者是"组织之间看不见"，后者是"同组织内我的是我的"。
一个单组织内网部署里，普通用户看到别人的知识库与应用，同样是错的。

## 二、角色重定义：把「使用者」与「建设者」分开

当前 4 个角色里，**前三个是岗位**（管理员 / 知识运营 / 应用配置），第四个是
「权限更少的岗位」。**缺的是"消费者"这个身份** —— 没有任何一个角色被设计成
「来用东西的，不是来建东西的」。

### 2.1 五个角色 + 一个非登录主体

| 族 | 角色 | code | 一句话定位 |
|---|---|---|---|
| **消费者** | **使用者** | `USER` | 只用别人做好的：问答、看引用、反馈。**界面上不出现任何"建设"语汇** |
| | 外部访客 | —（非角色） | 免登录，只走公开链接。**不是角色**，是凭证身份 |
| **建设者** | **个人建设者** | `CREATOR` | ★**新增**。能建**自己的**知识库与**简单**应用，发布给自己或小范围用 |
| | 知识运营 | `KB_OPERATOR` | 全平台知识库与文档治理、命中测试、反馈处理 |
| | 应用配置 | `APP_CONFIG` | 全平台应用配置、发布、编排 |
| | 管理员 | `ADMIN` | 账号、角色、模型、系统参数 |

### 2.2 为什么要把「普通用户」拆成两个

使用者的诉求是 **「无脑用」** —— 他不需要知道什么是分段、什么是向量化，
更不需要看到「上传文档」这个按钮。而个人建设者的诉求是 **「我也能弄一个」** ——
他需要建库、传文档、配一个简单应用，但**不需要**（也不该）碰全平台的资源。

合成一个角色的结果就是现在这样：为了照顾第二类人，把第一类人也丢进建设面。
**这是两个不同的人，应该是两个角色。**

`CREATOR` 的上限刻意收窄，写在权限点上：

- **能建**：知识库（自己）、简单应用（自己）、自己的会话与反馈
- **不能**：模型管理、提示词管理、编排应用、发布校验的绕过、看别人的东西、
  系统管理、运营看板（看板是全平台口径，给运营与管理员）

## 三、数据范围：必须引入「范围」这个维度

**不能靠加权限点解决。** `knowledge:view` 无论加多少个前缀都表达不了
「自己的 / 被共享的 / 全平台的」三种集合关系 —— 那是**范围**，不是**动作**。

### 3.1 资源侧：归属 + 可见性（三类资源统一）

知识库、应用、会话（含反馈）三类**用户产出**的资源，都加同样的三个字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ownerId` | `string` | 创建者。**不可变**（转让是显式动作，不是改个字段） |
| `visibility` | `'private' \| 'shared' \| 'public'` | `private` 仅自己 · `shared` 指定人或角色可见 · `public` 全平台可见 |
| `grants?` | `Grant[]` | 仅 `shared` 时有效。**不要用 `{ userIds, roleCodes }` 那种最简形状** —— 「共享」的演化空间最大，见 **§8.1**（那里给出了 `Subject` / `Grant` / `OwnedResource` 三个类型，MVP 只填其中两种主体） |

★ **`public` 不等于免登录。** `public` 是"登录用户里人人可见"；
免登录只有公开凭证（`AccessCredential`）那一条链路。两者混淆会造成越权。

### 3.2 角色侧：数据范围（三档）

`Role` 加一个字段（当前只有 `permissions: string[]`，没有表达位）：

| `dataScope` | 集合 | 典型角色 |
|---|---|---|
| `own` | 只有自己创建的 | 个人建设者 |
| `shared` | 自己创建的 **+** 被共享给自己的 | 使用者 |
| `all` | 全平台 | 知识运营 / 应用配置 / 管理员 |

（三档是**预设档位**，不是唯一形状 —— "本部门""我参与的项目"这类范围一定会来，
逃生口见 **§8.3**：先加枚举值，真需要表达式时才实现解析器。）

**为什么保留 `own` 与 `shared` 两档**（而不是只留 `shared`）：
`own` 的语义是**个人沙箱** —— 我只管我建的，别人分享给我的我也不想看见。
两者在"个人专注"场景下是不同的东西，合成一档就再也分不出来了。

### 3.3 可见性判定：全工程唯一一条

```
可见(资源, 我) =
     dataScope === 'all'
  || 资源.ownerId === 我
  || (资源.visibility === 'shared' && 我 ∈ 资源.sharedWith)
  || (资源.visibility === 'public' && 我持有 '<资源>:view' 权限点)
```

**三条硬规矩：**

1. **这条判定只在后端实现一次。** 列表查询、单条查询、写操作的**前置校验**三处都走它 ——
   写操作也要走，否则「看不见但能改」这种越权最难发现。
2. **前端的隐藏入口只是体验，不是安全边界。** 前端按 `dataScope` 少渲染几个模块，
   但**后端不认前端的渲染** —— 直接调接口必须被拒（这正是 `04` 验收项 A7 的口径）。
3. **不应答的语义要统一**：看不见的资源，单条查询一律返回 **404 而不是 403** ——
   403 等于告诉对方"这个 id 存在"。

| 建知识库 | ❌ | ✅ | ✅ | ❌ | ✅ |
| 上传文档 / 切分 / 向量化 | ❌ | ✅ | ✅ | ❌ | ✅ |
| 命中测试 | ❌ | ✅（限自己的库） | ✅ | ✅ | ✅ |

| 建**简单**应用 | ❌ | ✅ | ❌ | ✅ | ✅ |
| 建**编排**应用 | ❌ | ❌ | ❌ | ✅ | ✅ |
| 发布应用 | ❌ | ✅（限自己的） | ❌ | ✅ | ✅ |

| 系统管理 | ❌ | ❌ | ❌ | ❌ | ✅ |

> **提示词这一行为什么拆成两行**：类型是**分类法**（契约），配置是**内容**。
> 改一次类型，所有配置的归类、以及应用里「从提示词选用」的分组都会跟着变 ——
> 与「权限点清单」同族，所以归 `ADMIN` 维护；`APP_CONFIG` 只**引用**类型
> （选类别的下拉照常列得出全部类型），不新建/编辑/删除。
> 界面上的同族先例：权限点清单住在系统管理，而「给角色挂权限点」在角色管理里。

### 4.2 数据面（能看到哪些）

| 资源 | USER | CREATOR | KB_OPERATOR | APP_CONFIG | ADMIN |
|---|---|---|---|---|---|
| 知识库 | `shared`（只读） | `own` | `all` | `shared`（只读） | `all` |
| 文档 / 分段 | 不可见 | `own` | `all` | 不可见 | `all` |
| 应用 | `shared`（只读+可用） | `own` | `shared`（只读） | `all` | `all` |
| 会话 | **只有自己的** | 只有自己的 | 只有自己的 | 只有自己的 | **只有自己的** ⚠️ |
| 反馈 | 自己提交的 | 自己提交的 | `all` | 自己提交的 | `all` |
| 提示词配置 | 不可见 | 不可见 | 不可见 | `all` | `all` |
| 模型 | 不可见 | 不可见 | 不可见 | 只读 | `all` |

⚠️ **会话那一行需要拍板**（第四节）。

### 4.3 数据约束（引用与删除的完整性）

| 约束 | 规则 | 违反时 |
|---|---|---|
| 应用 → 知识库 | 应用只能绑定**对它可见**的知识库 | 保存时拒绝（不是发布时才拒） |
| 应用 → 模型 | 只能选**已加载成功**的模型（契约已有） | 发布校验拦下 |
| 删除知识库 | 被应用引用时**拒绝删除**，并列出引用方 | `409` + 可读原因 |
| 删除应用 | 有已发布版本时要求显式确认 | 需二次确认 |
| 会话 → 应用 | 会话挂在应用上；应用删除后会话**保留**（归因快照） | 保留即可，不做级联删 |
| 所有者变更 | 只能**显式转让**，且需 `ADMIN` 或原所有者发起 | 普通编辑不可改 `ownerId` |
| 个人建设者**离职/停用** | 其资源需可被 `ADMIN` 接管（不能变成孤儿） | 停用账号时提示接管入口 |

## 五、页面形态随之分化（这才是"感觉"的解法）

**只加数据范围还不够** —— 使用者看到的 `知识库` 页面如果还是那张"卡片列表 + 新建按钮"，
他还是站在工地里。**同一份数据，两种页面形态。**

| 角色 | 首页 | 导航 | 知识库页形态 | 应用页形态 |
|---|---|---|---|---|
| **USER** | **应用广场**（能用什么） | 问答 · 应用广场 · 我的反馈（**3 项**） | 不出现 | **应用广场**：卡片 + 「开始问答」，**无新建/配置/发布** |
| **CREATOR** | **我的工作台** | + **我的知识库** · **我的应用**（5 项） | **我的知识库**：自己的（可建可删） | **我的应用**：自己的简单应用（可建可发布） |
| KB_OPERATOR | 工作台 | + 知识库 · 命中测试 · 反馈处理 | 全平台知识库（含归属列） | 只读 |
| APP_CONFIG | 工作台 | + 应用管理 · 提示词 · 编排 | 只读 | 全平台应用（含类型切换） |
| ADMIN | 工作台 | + 模型 · 看板 · 系统管理 | 全平台 | 全平台 |

**两条判据（可直接当验收）：**

1. **`USER` 登录后，界面上不该出现任何一个"新建"按钮**，也不该出现
   「上传文档 / 切分 / 向量化 / 分段」这类**建设语汇**。
2. **`CREATOR` 登录后，不该看到任何"别人的"资源** —— 他的知识库列表里
   只有他自己建的（以及明确分享给他的）。

★ 这也顺带解决了「工作台指标条」的角色问题：现在的 4 项指标
（问答次数 / 活跃用户 / 满意度 / 待处理反馈）是**全平台口径**，
对 `USER` 与 `CREATOR` 没有意义 —— 他们的首页该是「我的」口径
（我的提问数 / 我的应用 / 我的待处理），或干脆换成**应用广场**。

## 六、契约差距与迁移路径（契约是冻结的）

**这是本册最需要注意的地方。** 前端契约已冻结（`ROADMAP.md`），
加 `ownerId` / `visibility` / `sharedWith` 属于**破坏性变更**。
但有一条低风险路径 —— **只加可选字段 + 后端先落地过滤**：

### 阶段 1 · 后端落地（前端零改动即可工作）

- 创建类 `POST` **由后端自动写** `ownerId = 当前用户`、`visibility = 'private'`
  ⇒ 契约**不需要新增请求字段**
- 列表类 `GET` **由后端按 `dataScope` 过滤** ⇒ 契约不需要新增请求字段
- 契约只**新增可选响应字段** `ownerId?: string` / `visibility?: string`，
  以及一个可选的查询参数 `mine?: boolean`
  ⇒ **前端不传、不读，也照常工作**（这是"冻结契约"下唯一安全的加法）

### 阶段 2 · 前端按 `dataScope` 分化

- `Role` 加可选字段 `dataScope?: 'own' | 'shared' | 'all'`
- 导航过滤从「只看权限点」改成「权限点 **且** 有该范围的资源形态」
- 知识库/应用页按角色切形态（`我的` vs `全平台`）

### 阶段 3 · 共享 UI 与转让

- `sharedWith` 的编辑界面、资源转让入口、管理员接管入口

★ **阶段 1 就能单独发布**：它把"越权可见"从架构上关掉，
而前端一行不改 —— 这也是本工程一贯的做法（契约先冻结、后端在被约束下实现）。

## 七、需要拍板的四件事

| # | 问题 | 备选 |
|---|---|---|
| 1 | **管理员能不能看别人的会话？** | (a) **不能**（会话是私人对话，管理员只看聚合指标）· (b) 能，但需留痕 · (c) 能，用于质检 |
| 2 | **`CREATOR` 能不能建编排应用？** | (a) **不能**（编排是专业能力，归 `APP_CONFIG`）· (b) 能，但限节点数 · (c) 能 |
| 3 | **`public` 可见性要不要在 MVP 就有？** | (a) **MVP 只做 `private`**，`shared`/`public` 留 V0.2 · (b) 三档一起 |
| 4 | **新建知识的默认可见性** | (a) **`private`**（安全默认，要共享得显式动作）· (b) `shared` 全组织可见 |

> 建议：**1(a) · 2(a) · 3(a) · 4(a)** —— 四条都是"默认收窄、要放开得显式动作"。
> 理由：数据权限这种东西，**放开容易、收回难**（一旦有人习惯了能看全部，再收就是"功能退化"）。
> 反过来先收窄，需要时再放开，是一次纯增益的变更。

## 八、扩展口径（为后续留的口）

> 原话是：*「现在想不到那么多，但最好可以有扩展的空间。」*
>
> **这一节不是"把将来的功能都设计了"，而是把将来会长的地方换成"能长的形状"。**
> 每一条都只是**改变字段的表示**，**不增加当前工作量** —— 这是它与"过度设计"的分界线。
> §8.8 明确列出**不做**的那些，正是为了守住这条线。

### 8.1 ★ 最大的一个口：用 `grants` 表达共享，而不是 `{ userIds, roleCodes }`

最简形状是 `sharedWith: { userIds: string[]; roleCodes: string[] }`。它只够表达
"共享给这几个人和这几个角色"。而**「共享」这个概念的演化空间是全模型里最大的** ——
迟早要加：共享给部门、只读 vs 可编辑、有效期、可再分享、链接共享。

所以字段就**取那个能长的形状**（MVP 只填 `user`/`role` 两种主体、每类资源一个动作）：

```ts
type SubjectKind = 'user' | 'role' | 'org' | 'group' | 'link'
interface Subject { kind: SubjectKind; id: string }

interface Grant {
  subject: Subject
  actions: string[]           // 与权限点同一套词汇：knowledge:view / assistant:edit …
  expiresAt?: string | null   // 时效
  canDelegate?: boolean       // 可再分享
}

interface OwnedResource {
  ownerId: string
  visibility: 'private' | 'shared' | 'public'
  grants?: Grant[]
}
```

**加"共享给部门" = 加一个 `SubjectKind`；加"只读/可编辑" = 每条 grant 多一个 action；
加"有效期" = 填 `expiresAt`。** 三种扩展都**不动判定函数、不动表结构、不动契约形状**。

★ 反面做法是把 `sharedWith` 写成两个数组 —— 那时上面三种扩展每一种都要**改字段**，
而字段一改，前端、后端、数据库一起动。**这是本册成本最低、收益最高的一处形状选择。**

### 8.2 判定接收「主体集合」，不接收「当前用户」

```
可见(资源, 主体集合 S) =
     scope(角色) === 'all'
  || 资源.ownerId ∈ S.ids
  || ∃ g ∈ 资源.grants: g.subject ∈ S 且 动作 ∈ g.actions
  || (资源.visibility === 'public' 且 动作 ∈ 主体权限点)
```

`S` = `{ 该用户, 其角色, 其部门, 其项目组, … }`。现在只填**用户与角色**两项；
将来加"部门""项目组"只是**往集合里多塞一项** —— 判定本身一个字不改。

★ 这也是**外部协作者**的接入点：外部人也是主体，只是来源不同。

### 8.3 `dataScope` 是**预设档位**，不是唯一形状

`own | shared | all` 覆盖现在能想到的全部。但"本部门""本部门及下级""我参与的项目"
这类需求一定会来。所以：**枚举保留为预设档，同时留一个规则字符串的口子**：

```ts
dataScope: 'own' | 'shared' | 'all'   // 预设档，覆盖绝大多数场景
dataScopeRule?: string                // 逃生口：结构化规则（先不做解析器）
```

MVP **只实现枚举**，`dataScopeRule` 留空且不读。将来加"本部门"时的正解是
**先加一个枚举值 `'org'`** —— 大多数情况下这就够了；真需要表达式时才去实现解析器。

### 8.4 归属与判定做成**可复用形状**，不要每类资源写一遍

现在三类资源（知识库 / 应用 / 会话）。将来还有文档、分段、提示词、数据集…
所以：**后端一个 `OwnedResource` 接口 + 一个判定入口；前端一个 `ResourcePolicy` 类型。**
加一类资源 = 实现同一个接口，**判定逻辑零复制**。

★ 判据：**如果加第四类资源时你需要复制判定函数，说明形状选错了。**

### 8.5 判定必须**可下推为 SQL 谓词**（性能口）

```sql
WHERE owner_id = :me
   OR visibility = 'public'
   OR EXISTS (SELECT 1 FROM grants g
               WHERE g.resource_id = r.id
                 AND g.subject IN (:subjects)
                 AND :action = ANY(g.actions))
```

**不许"取全量再在内存里过滤"** —— 那是把权限做成 O(n)，
数据量一上来要么慢、要么被人绕过分页。这一条是**实现约束**，
但必须现在写下来：**等到列表分页之后再改，就要动查询结构。**

### 8.6 与多租户**正交**，表达为可组合谓词

```
可见 = 租户内(资源) AND 范围匹配(资源, S)
```

将来开多租户只是**与**上一个条件（`AND tenant_id = :t`），范围逻辑一个字不改。
这正是 §一 里"多租户可以推、数据权限不能推"的结构化表述 —— **两者是可乘的，不是二选一。**

### 8.6.1 ★ 密级：第三个正交维度（`13` 册）

```
可见 = 租户内(资源) AND 范围匹配(资源, S) AND 密级(资源) ≤ 我的上限
```

★ **密级与 `dataScope` 正交**：范围回答"**谁的**"，密级回答"**多敏感**" ——
一份"我自己的"文档可以是**机密**，一份"全平台可见"的文档可以是**公开**。
**把两者混成一个字段，会出现"因为是我建的所以能看机密"这种荒谬结论。**

⇒ 完整设计（等级 + 标签的模型 · 传播与漂移 · **五道闸门** · RLS × HNSW 的坑 ·
引用与分享隔离 · 审计 · **P0→P3 落地分期**）见 **`13-密级与数据隔离设计.md`**。

★ **与本册的关系**：它是同一个"**可组合谓词**"思路的第二个使用者 ——
判定入口**仍然是唯一的**（§8.7），只是那个入口现在要同时管"归属范围"与"密级上限"两个条件。

### 8.7 判定**单一入口**，为了将来能挂审计

"谁看了谁的数据""谁把资源分享给了谁"，这类问题上线后一定会被问。
判定只有一个入口，**审计就只有一个挂载点**。

★ 这也是 §3.3「只在后端一处实现」的**第二个理由**：
第一个理由是安全（避免漏一处就漏一处洞），第二个理由是**可观测**。

### 8.8 明确**不做**的（防过度设计）

| 不预留 | 理由 |
|---|---|
| 规则表达式的**解析器** | 先加枚举值通常就够（8.3）；真需要时再实现 |
| 角色的继承链 / 角色树 | 现在角色是平的，加继承要动判定顺序 —— 「要了再说」 |
| ABAC / 属性策略引擎 | 属性来源（部门、项目）本身都还不存在，先做等于空转 |
| 资源内的**字段级**权限（同一行不同字段可见性） | 复杂度极高，且与"整行可见性"是两个不同的问题 |
| 跨组织的委派 | 与多租户同批（V2.0） |

★ **8.1–8.7 与这五条的区别**：前者是**换形状**（零额外工作量，现在就该做）；
后者是**加机制**（有成本，等有需求再做）。**只做前者。**

## 十、组织机构树（★ 数据权限的载体，第 19 周前的形状收口）

### 10.1 为什么它现在就要落形状

今天"责任部门"是 `kb_document.department varchar(64)` 上的**一个自由字符串**，前端只给建议值
（`DEPARTMENT_SUGGESTIONS`）。这有三个后果：

1. **它进召回前缀**（`12 §4.2`：`search_text = 文种|部门|标题|路径|正文`），所以它不是一个纯展示字段；
2. **它进 `content_hash`**（`SEG-I7`）⇒ 改部门名会让该部门下所有文档"前缀变了 ⇒ 需要重新向量化"；
3. ★ **它没法做数据权限**：字符串比不出"我的部门 + 下级"，也没法作为共享主体。

⇒ 数据权限（`§五/§六`）要真正按组织隔离，**必须先把部门实体化**：
`department` 字符串 → `kb_document.org_id`（外键）。★ 这属于 `13 §8.2` 那条判据
（"会进 SQL 谓词或改数据形状"）⇒ **必须在库里还没量产数据时改**，晚了就是回填 + 全量巡检。

### 10.2 `iam_org` 的形状：物化路径，不用递归 CTE

| 列 | 说明 |
|---|---|
| `id` / `code` | `code` 是**稳定的机器码**（进 grants 的 `subject_id`，也进 JWT/审计），改名不改码 |
| `parent_id` | 自引用；根节点的父为 null |
| `path` | ★ **物化路径**（形如 `/root/procurement/`），"含下级"= `path like :prefix \|\| '%'` |
| `sort` / `enabled` | 排序与启停（停用的部门不参与新的共享，但**不影响既有数据**） |
| `name` | 展示名。★ **改名会让前缀变 ⇒ 该部门下文档需要重新向量化**（§10.1 第 2 条），要提示 |

★ 为什么用物化路径而不是递归 CTE：**数据权限要在每一条检索 SQL 里生效**（`13 §三` 的 pre-filter），
而"我的部门及下级"在物化路径下是一个**字符串前缀比较**，planner 能用上索引；
递归 CTE 放进每一条检索查询，既难读又难被 planner 优化。代价是**移动部门要重写子树路径**
（一次 `update ... where path like ...`），而移动是低频操作。

### 10.3 与既有两套机制的关系（★ 别再出现"同一件事两处真相"）

| 机制 | 管什么 | 与组织树的关系 |
|---|---|---|
| `DataScope`（`ALL/SHARED/OWN`，进令牌） | **账号级**：这个人默认看多大范围 | ★ **本版不加档**（见下） |
| `kb_knowledge_base_grant`（`subject_kind` ∈ USER/ROLE/**ORG**） | **资源级**：某条资源额外共享给谁 | ★ 组织树的**第一个消费者**：`ORG` 分支按 `path` 前缀判"含下级" |
| `ScopeFilter.canSee` | 上面两者的**唯一**判定点（`§3.3` 硬规矩 1） | 加 `ORG` 分支时**只改这一处** |

★ **本版不给 `DataScope` 加"部门档"**，理由：那三档是**账号级**的，加档要同时动
令牌声明、仓储的 `search(scope,…)`、前端 `scopeForms` 三处；而"共享给部门"用**现成的 grant 机制**
就能表达（`SubjectKind.ORG` 早已预留）。等到出现"新文档自动对本部门可见"这类**非显式共享**的需求，
再加档——那时也只需要在 `ScopeFilter` 一处加分支。

### 10.4 用户归属

`iam_user.org_id`（可空：还没来得及归类的账号）。★ **一人一部门**（MVP）：
多部门归属会让"我的部门及下级"变成集合运算，而共享主体（grant）本身就已经是集合语义了 ——
如果将来真要一人多部门，正确的做法是加一张 `iam_user_org`，**不是**把 `org_id` 改成数组。

### 10.5 判据

1. 把一条知识库共享给某部门 ⇒ 该部门的人（**含下级**）看得见；**别的部门的人看不见**（含兄弟部门）。
2. 移动一个部门到别处 ⇒ 它的下级跟着走（`path` 前缀重写），**共享关系不失效**。
3. 停用一个部门 ⇒ 不产生新的共享，**既有共享不变成不可见**（停用 ≠ 撤销）。
4. ★ 金丝雀：把 `ScopeFilter` 里 `ORG` 分支的"含下级"改成"精确匹配" ⇒ 判据 1 必须变红。
