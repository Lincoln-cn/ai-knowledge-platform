## 一、方法（读数的口径，先钉住再谈数字）

- **一个库一份读数**：每次运行新建一个知识库，避免历史文档/分段污染行数比对。
- **触发一次不重试**：70 个 `POST /api/v1/documents/{id}/embedding` 各发一次（16 线程并发发，
  只影响"触发窗口"这一项读数），记录 `接受 / 5xx / 4xx / 窗口秒`。**脚本不做任何自动重试**。
- **采样与灌入并发**：`PgSampler` 复用**一个持久 psql 会话**（`docker exec -i … psql -f -`，逐条写
  SQL 再读一行），每 200 ms 取一次 `pg_stat_activity`。单次 `docker exec` 约 0.9 s，撑不起 200 ms
  采样，所以必须复用会话而不是每帧起一个 psql。
- **只数自己那套连接**：采样 SQL 带 `pid <> pg_backend_pid()`（排除采样自己），并用
  `application_name = 'gate227'` 把本实例的连接挑出来 —— 本机同时有别的后端在跑（18088 / 18092，
  各自占 10 条 idle 连接），不分域就会把别人的连接读成我们的。
- **两类 `EMBEDDING_FAILED` 分开计数**（issue 明确要求）：
  - `concurrency`：文案含 `Failed to obtain JDBC Connection` / `CannotGetJdbcConnectionException` /
    `Unable to acquire JDBC Connection` / `Connection is not available` / `HikariPool` /
    `数据库连接池被同时入库的任务占满`；
  - `model_missing`（`#228` 那副面孔）：含 `向量模型不存在` / `no such embedding model` /
    `EmbeddingModelNotFound`；
  - `other`：都不匹配的（本轮出现的 `Could not open JPA EntityManager for transaction` 就落在这里，
    见 §六 —— 它其实是并发同一根因，是**旧判据漏认**）。
- **行数比对三口径**：`kb_segment` 行数 / `vec_embedding_384` 里 `metadata::jsonb->>'kb_id'` 命中数 /
  两者 join 的数量。三口径一致才算"行数相等"，否则中间那种写法会把"少写了几行"读成相等。

才得到"只变慢"。

|---|---:|---:|---:|---|---:|---:|---:|---|---|

- **C vs A**：9.524 / 7.009 = **1.36×**（总耗时 190.49 / 140.18 = 1.36×）。
- **C vs B**：9.524 / 7.591 = **1.25×**（190.49 / 151.82 = 1.25×）。
- ★ 为什么给两个基线：同一构建、同一配置的两次运行差 8%（140.18 vs 151.82）。修复前那一构建的
  20 份读数是 289.38 s —— 跨 JVM 波动能到 2×。因此"变慢"的结论只能按 **1.25–1.36×** 报，

★ 这条 hint 把"连接池不够"说成了"文件有问题" —— 与 `#227` 主治的那个病同一个形状（`silent-failure`），

## 六、反证顺手暴露的真问题：`isResourceExhaustion` 漏认 Hibernate/JPA 的两种包装

反证第一跑（`kb=37f305c3-…`，JVM 被我杀掉）留下 40 份 `EMBEDDING_FAILED`，按文案分两串：

| 文案 | 份数 | 归到哪个分支 |
|---|---:|---|
| `向量化失败：数据库连接池被同时入库的任务占满（资源不足，不是文档的问题）` | 15 | 资源不足（`isResourceExhaustion` = true） |
| `向量化失败：Could not open JPA EntityManager for transaction` | **25** | **普通失败**（`isResourceExhaustion` = false） |

第二串里没有任何"连接池"字样，用户只会看到"向量化失败" + hint「请确认模型服务可用后重试」——
**同一根因（池打满）被报成两个互相矛盾的结论**，25/40 的分支还指错了排查方向。

根因（日志的 cause 链）：Hibernate 把 Hikari 的超时包成 `org.hibernate.exception.JDBCConnectionException`
（再上一层是 `jakarta.persistence.PersistenceException`），**两种都不是 Spring 的异常**，而旧判据只认
`DataAccessResourceFailureException` 及其子类。

**修法**（只改 `backend/src/main/java/cn/lincoln/aiplatform/knowledge/application/EmbeddingRunner.java`
的 `isResourceExhaustion`，不动控制流）：

```java
for (Throwable current = error; current != null; current = current.getCause()) {
  if (current instanceof DataAccessResourceFailureException
      || current instanceof SQLTransientConnectionException) {   // ← 新增：Hikari 真正抛的那个
    return true;
  }
  String message = current.getMessage();
  if (message != null
      && (message.contains("Connection is not available")          // ← Hikari 的措辞
          || message.contains("Unable to acquire JDBC Connection"))) {  // ← Hibernate 的措辞
    return true;
  }
  if (current.getCause() == current) break;
}
```

★ 两处刻意的取舍：

1. **不 import Hibernate 的类型**：`knowledge` 的应用层不该依赖 ORM 实现；上面的两句文案是
   Hibernate 与 Hikari 各自的固定措辞（它们改了，这里就该复核）。
2. **判据仍然放窄**：只加"连接池/连接获取不到"这两种形状，没有退化成"任何 `DataAccessException`
   都算资源不足" —— 唯一约束冲突、SQL 写错靠重试好不了，归成资源不足会让用户无限重试
   （原实现的注释已经把这个理由写下来了，本轮沿用）。
3. **没有补单测**：本轮的写面只允许 `EmbeddingConcurrencyGate` / `EmbeddingRunner` / `application.yml`
   的池参数，测试文件不在其中 ⇒ `EmbeddingFailureClassificationTest` 未增用例。

**这个修改是"真补上了"还是"只是换了个写法"—— 用一次 A/B 探针取证**（`.build/gate227/probe/` 下，
包内探针，编译进 `backend/target/classes` 的类路径；**同一批用例上同时跑新旧两份判据**）：

| 用例 | 新判据 | 旧判据 |
|---|---|---|
| `new SQLTransientConnectionException("HikariPool-1 - Connection is not available, request timed out after 32310ms …")` | **true** | **false** |
| `new PersistenceException("Could not open JPA EntityManager for transaction", new JDBCConnectionException("Unable to acquire JDBC Connection", …))` | **true** | **false** |
| `new RuntimeException("Could not open JPA EntityManager for transaction", new RuntimeException("Unable to acquire JDBC Connection"))` | **true** | **false** |
| `new IllegalStateException("批写入失败", new DataAccessResourceFailureException("connection is not available"))` | true | true |
| `new DataIntegrityViolationException("duplicate key value violates unique constraint")` | false | false |
| `new IllegalArgumentException("段数不一致")` | false | false |

⇒ **旧判据在前三行全为 false**（这正是反证那轮 25/40 份被报成「向量化失败：Could not open JPA
EntityManager for transaction」的原因），新判据为 true；两个反例新旧都为 false（没有扩大成"任何
`DataAccessException` 都算资源不足"）。探针输出：`探针通过：6/6`。

★ 一点要如实说：真栈上**没能再复现**"修复后的反证轮也失败"——用 20 份压闸门关的修复版，池 10 撑住了
（20 份全成功、140.05 s、峰值 `active` **10/10**、1 帧顶到上限），没制造出连接池超时，所以这次的
运行时取证只到"峰值把池占满"为止，分类修复的取证靠上表的 A/B 探针。

## 七、吞吐瓶颈不在闸门、也不在池（读数外的发现，建议另开 issue）

- 实测写入速率约 **5 条向量/s**（70 份 5517 段 ⇒ 473 s，与 20 份 1743 段 ⇒ 140 s 同量级）。
- 同期 10 秒增量：`xact_commit +173` / `tup_inserted +166` / `tup_updated +42` ⇒ **DB 侧不是瓶颈**；
  Java 进程 10 秒内 CPU 时间 +33 s（≈333%）⇒ 瓶颈在算/锁。
- 锁在哪：`JdbcVectorIndex.upsert` **每一段**都调 `ensureTable(dimension)`，跑两条 DDL。实测
  `create index if not exists idx_vec_384_hnsw … using hnsw (embedding vector_cosine_ops) with (m=16, ef_construction=64)`
  **即使索引已存在也要 71.8–76.6 ms**（取 `ShareUpdateExclusive` 锁、跨会话串行化），btree 那条
  `idx_vec_384_kb … ((metadata::jsonb->>'kb_id'))` 只要 3.4 ms。每段 ≈80 ms 纯 DDL ⇒
  5517 段 × 73 ms ≈ **403 s**，正好是整批耗时的主体。
- 这条同时解释了**原事故的机理**：连接被"每行 80 ms 的 DDL"长时间占住 ⇒ 池被占满 ⇒ 后面拿连接的
  请求 30 s（Hikari 默认 `connection-timeout`）后失败 ⇒ `Failed to obtain JDBC Connection`。
  闸门把并发限住之后，"占住"的总量没变，但**排队的人在闸门外**而不是在 Hikari 里超时，于是从
  "失败"变成"慢"。
- `JdbcVectorIndex` 不在本轮写面内 ⇒ **只报告不改**。建议：`ensureTable` 每个 `dimension` 只做一次
  （进程内缓存 + 启动预热），预期吞吐提升一个数量级。

## 八、解析路径没有闸门（同一形状的第二个洞）

`EmbeddingConcurrencyGate` 只包在**向量化**任务外面；**解析/分段**仍然"每份文档一个虚拟线程、无上限"。
池压到 2 时先炸的是解析（§四 D 轮）：4 份 `SEGMENT_FAILED`、8 份卡在 `SEGMENTING` 不落地、
hint 还写着"请确认文件可正常打开"。

- 卡住的那 8 份是**真的卡住**：`updated_at` 全部停在 `10:10Z`，20 分钟后 `pg_stat_activity` 里我方
  连接 `active=0 / idle=2` ⇒ 没有线程在等连接、也没有线程在跑，状态再也不会变。
- 这一条超出本轮写面（`DocumentService` / `ParseRunner` 不在允许改动清单里）⇒ **只报告**，建议另开
  issue：解析侧要么也过闸门，要么至少把"资源不足"与"文件坏了"分开报（与 §六 同一判据）。

## 九、没做到的 / 读数的边界

1. **没有补单测**：`isResourceExhaustion` 的新分支用 §六 的包内探针取证（A/B 对照、6/6），没有进
   `EmbeddingFailureClassificationTest`（写面限制：本轮只允许改 `EmbeddingConcurrencyGate` /
   `EmbeddingRunner` / `application.yml` 的池参数）。把那张 6 行表原样搬成一条 JUnit 用例，是
   后续必须补的闸门 —— 现在它靠一份**不在仓库里**的探针守着，下一个人看不到。
2. **判据③的"变慢了多少"精度有限**：1.25–1.36× 与同构建两次基线的 8% 波动、跨构建 2× 波动同量级。
   本轮只能断言"按闸门容量串行化、不变失败"，不能断言固定倍数。
3. **闸门容量是"声明值"不是"运行时读回值"**：没有 actuator 端点暴露 `EmbeddingConcurrencyGate.capacity()`，
   脚本按 `--gate-capacity` 记声明值；运行时唯一佐证是启动自检日志。读数里凡标"闸门 4 / 1 / MAX"的，
   都对应一条那样的启动日志。
4. **只测了单实例、单机 DB**：池上限与 `max_connections=100` 的余量、多实例共享一个库时的表现，本轮没测。
5. **池=2 的那两轮都用了串行灌入**（`--upload-serial`）：因为解析侧没有闸门，20 份同时解析会先把池打满，
   测到的就不是"向量化批次"。这意味着**判据③量的只是向量化那一段**；整链（解析+向量化）在池=2 下的
   表现按 §四 D 轮如实报"失败"。
6. **没有跑整包测试**（项目规矩：不跑 `mvn verify`）。既有 4 条分类断言按单类跑过、未回归：
   `mvn -o test -Dtest=cn.lincoln.aiplatform.knowledge.application.EmbeddingFailureClassificationTest` ⇒
   `Tests run: 4, Failures: 0, Errors: 0`。但**新分支本身没有用例**（见第 1 条）。
