# 执行引擎缺口与接线路径（`#326` 交接）

> 2026-11-10 整理。本文记录 `workflow` 执行引擎"发布放行但跑不了"这件事的完整账：
> 缺口在哪、已经补了什么、为什么现在跑不起来、下一个人应当从哪下手。
> 设计口径仍以 `docs/ROADMAP.md` 与设计册为准，本文只记**实测到的事实与读数**。

## 一、问题是什么

`WorkflowValidationService` 的 `NODE_NOT_EXECUTABLE` 规则（批次 1 的 `4dc4248`）在**发布时**用
`LinearWorkflowExecutor.SUPPORTED_TYPES = {START_NODE, SEARCH_DATASET_NODE, AI_CHAT_NODE, REPLY_NODE}`
判断"这些类型能跑"。而运行时 `NodeExecutorRegistry` 里一个实现都没有 —— 于是：

- 发布**通过**；
- 用户配好、点试用 ⇒ `IllegalStateException: 没有类型 SEARCH_DATASET_NODE 的节点执行器`。

根因不是"忘了写执行器"。`NodeExecutor` 的 javadoc 写得很清楚：「执行器只依赖 `WorkflowNodeContext`，
不碰任何跨模块服务 —— 真跑 `AI_CHAT_NODE` 要接 `conversation` 的 `ChatService` 会越模块边界，本版本刻意不接」。

⇒ 真正的矛盾是：**那个常量描述的是"理论上限"，发布校验把它当成了"当前装配"**。

## 二、★★ 整条链是断的（2026-11-10 查实）

这一节是本文最重要的部分。上面的"没有执行器"只是最表面那一层，往上看还有三层。

```
$ WorkflowRecordRepository 接口的全部方法
    List<WorkflowRecord> page(UUID assistantId, String status, int page, int size);
    long count(UUID assistantId, String status);
```

**没有 `save`。** 这个接口是 `assistant/domain` 里唯一的记录仓储 ⇒ `as_workflow_record` 在整个主代码里**没有任何写入方**。

```
$ LinearWorkflowExecutor 的引用方
assistant\application\LinearWorkflowExecutor.java     ← 定义
assistant\application\NodeExecutor.java               ← javadoc 提到
assistant\application\WorkflowNodeContext.java        ← javadoc 提到
assistant\application\WorkflowValidationService.java  ← 引用（只读 SUPPORTED_TYPES 常量）
```

⇒ **`LinearWorkflowExecutor.execute(...)` 在主代码里没有调用方。**

### 所以缺口是四层

| 层 | 缺什么 | 状态 |
|---|---|---|
| 1 | 一次执行的**起点**：谁触发、从哪进来 | **没有**（`#295` 触发器只留了数据列） |
| 2 | 创建执行记录（`WorkflowRecordRepository` 缺 `save`） | **没有** |
| 3 | 调用 `LinearWorkflowExecutor.execute` | **没有** |
| 4 | 节点执行器本身 | 已补 `START_NODE` / `SEARCH_DATASET_NODE` |

**已交付的 6 个提交补的是第 4 层**。它本身没错（配置链路、端口、身份通道都是真实缺口，见下），
但它上面三层全空 —— 所以现在这套东西跑不起来，不是因为哪一行写错了，是因为**没有起点**。

★ 第 1 层是产品决策，不是实现决策。三种可能：用户点「试用」（`workflow/debug`，`#113`）、
触发器（`#295`）、外部 API 触发（API Key）。在拍板之前，第 2/3 层写出来也是空转。

### 配置链是怎么通的

链路原本是：画布 JSON 的 `properties.config` → `Node(id, type)`（**丢掉**）→ `PlanStep(nodeId, type, order, branchHandle)`。

★ 关键发现：`Graph(List<Node> nodes, List<Edge> edges)` 是**直接从画布 JSON 反序列化**的 ——
`grep -r "new WorkflowCompiler.Node(" backend/src/main/java` 零命中，测试里也零命中。
所以配置一直在 JSON 里，只是 record 没声明字段，Jackson 填的时候丢了。**加一格即可，不需要改解析逻辑。**

判据 `carriesNodeConfigFromCanvasJsonToPlanStep` 必须走 JSON 反序列化，用 `new Node(id, type, properties)` 造出来的节点
证明不了"Jackson 填进来了" —— 那正是加字段之前一直没被发现的原因。

## 四、检索实现这一侧

`knowledge` 模块要提供 `WorkflowSearchPort` 的实现（`SegmentSearchPort` 按 `userId` 生成密级与组织 scope）。

★ 注意位置：`JdbcSegmentSearchQuery` 在 **`knowledge/infrastructure/`**，不在 `retrieval`。
而 `assistant` 的 `@ApplicationModule(allowedDependencies = {"platform", "identity", "modelcatalog", "knowledge"})`
**已经包含 `knowledge`** ⇒ 实现放 `knowledge` 是顺着现有依赖方向走，不需要绕 `retrieval`
（`retrieval/package-info.java` 末尾写明「它不得依赖 conversation」，硬塞进 `retrieval` 可能引出新的跨模块边）。

★ 但**现在不能先写 adapter**：`userId` 仍是 `null`（第 2 层没有写入方），
先写 ⇒ 它拿到的永远是 `null` ⇒ 只剩两条路：按系统身份查（等于绕过密级）、或者不查（功能缺失）。

## 五、`AI_CHAT_NODE` / `REPLY_NODE`

`assistant` 的模块声明里**没有 `conversation`**。`AI_CHAT_NODE` 要对话能力，同检索一样得在 `platform` 立端口。
`REPLY_NODE` 大概率只需要读 `state`，成本最低，可以先做。

## 六、判据设计（下一步照这个写）

1. **起点**：先定第 1 层走哪条路，然后**从那条路开始写集成测试** —— 不是从执行器开始。
2. **按人过滤**：同一条工作流，A 用户跑与 B 用户跑（两人密级不同）⇒ 检索到的段集合不同。
   ★ 这是"检索真的按人过滤了"的唯一硬证据。
3. **`REPLY_NODE`**：`state` 里有内容 ⇒ 回复节点产出非空。
4. **`NodeExecutorRegistryTest` 的反向断言**：`KNOWN_UNIMPLEMENTED` 必须是实际差集，现在等于 `{AI_CHAT_NODE, REPLY_NODE}`。

## 七、几条这一批踩出来的通用教训

1. **"某条路径能跑"不等于"这类路径都能跑"** —— `#324` 的懒加载 500 只在「从模板 instantiate 出来的应用」上炸。
2. **先查"这个数据是怎么进来的"，再决定改哪一层** —— 一度判定要改三处解析逻辑，实际只是 record 加一格。
3. **判断执行器"有没有做"，不能看它注册成功，要看它在一条真实计划里能不能产出数据** ——
   `SearchDatasetNodeExecutor` 第一版写了一半撤回，因为它永远 `return null`，但注册表会认它、判据会变绿，**比没有更糟**。
4. **端口不给 `noop()` 兜底** —— 一个永远返回空列表的兜底会让「没命中」和「没装配」读数完全一样。
5. **改 record 的 canonical 构造器后，旧的兼容构造器会静默变成递归委托** —— 必须显式补一个中间构造器。
6. **"某个接口没有 save 方法"是一个可以一眼查出来的信号** —— 查"这条链有没有起点"，先看仓储接口有没有写方法，比顺着调用栈找快得多。
