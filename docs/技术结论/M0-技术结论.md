## 结论一：各模型的「思考模式」三态取值

**问题**：计划支持的每个模型，分别属于哪一态？

**口径来自冻结契约**（`frontend/src/api/models.ts:6-9`）：

```ts
/** 模型能力三态，决定界面开关如何呈现（思考模式） */
export type ThinkingMode = 'NONE' | 'TOGGLEABLE' | 'ALWAYS_ON'
```

| 取值 | 含义 | 界面行为 |
|---|---|---|
| `NONE` | 不支持思考 | 开关不出现 |
| `TOGGLEABLE` | 可开关 | 开关可切换 |
| `ALWAYS_ON` | 始终思考，关不掉 | 显示"始终开启"，置灰不可切 |

★ 契约还要求标注这个值是**「探测」还是「手工声明」**（`models.ts:48` 的
`ModelCapability.source`）—— 遇到探测不准的模型，界面要允许人工覆盖，
且**必须看得出哪个是人工填的**。这条约束会影响 `modelcatalog` 的数据形状（`source` 要落库）。

**怎么测**：对每个模型问同一个**需要推理**的问题，两次 ——
① 不传任何思考参数；② 显式要求关闭思考。对比两次响应里"思考痕迹"的有无。
探针用**原始 HTTP**取完整响应（思考内容通常走 `reasoning_content` 这类独立字段，
只看 `content` 会把"模型在思考"误判成"没思考"）。

**判据**：

| 观察 | 判定 |
|---|---|
| 两次都没有思考痕迹 | `NONE` |
| ① 有、② 没有 | `TOGGLEABLE` |
| 两次都有 | `ALWAYS_ON`（★ 但**必须先排除"是我们没传成功"** —— 见结论二，而框架侧已证会下发） |

**结果**：⏳ 待填（由探针输出）

| 模型 | 判定 | 证据（首次是否含思考 / 关思考后是否消失） | 备注 |
|---|---|---|---|
| | | | |

## 结论二：Spring AI 能否下发「思考开关」

**问题**：Spring AI 2.0.1 的 `OpenAiChatOptions.reasoningEffort(...)` 能否把开关**真的送到上游**？

**为什么这条最容易出错**：结论一的 `TOGGLEABLE` 与 `ALWAYS_ON` 之分，
**依赖"我们能成功关掉思考"这个前提**。如果框架根本没把参数发出去，那么所有模型都会被误判成
`ALWAYS_ON` —— 这个错误一路传到界面，表现是"这个模型的思考开关点了没反应"，
而排查时会先怀疑模型，**方向就错了**。

### 结果：两侧分开记

| 侧 | 结论 | 证据 |
|---|---|---|
| **框架侧** | ✅ **会下发** | ★ 实测（`OpenAiStubContractTest`，桩服务侧记录请求体）：给出 `reasoningEffort` 后，请求体里**出现** `reasoning_effort`；不给时不出现。两个方向都验了，所以不是"碰巧总有" |
| **上游侧** | ⏳ **待真模型** | 桩服务"接受"这个字段是我自己写的，**不构成证据**。需要真 Ollama 来判断它在 OpenAI 兼容端点上认不认 `reasoning_effort` |

**判据与后果**（框架侧已确定，只剩上游侧）：

| 框架侧 | 上游侧 | 结论 | 我们要做什么 |
|---|---|---|---|
| ✅ 会下发 | 接受 | ★ 最好 | 直接用，零自研 |
| — | **不认这个字段** | 上游问题 | 改用 Ollama **原生** `/api/chat` 的 `think` 参数 —— 会改端口实现，但不影响业务代码 |

> ★ 顺带被这次实测**确认**的一件事：`application.yml` 把
> `base-url` 写成 `http://localhost:11434/v1` 是**对的**。
> 证据：桩服务记录到的真实请求路径是 `/v1/chat/completions`，**不是** `/v1/v1/chat/completions`。
> 这条以前是"照着 Ollama 文档推的"，现在是实测值。

## 结论三：能否稳定产出结构化输出

**问题**：`ChatClient...call().entity(SomeRecord.class)` 在同一个小模型上连续调用，能否**稳定**返回合法 JSON？

**为什么不是"能不能返回 JSON"**：单次成功没有意义。我们的用法（查询改写、子问题分解、
行级陈述化的 LLM 变体）是**每个请求都跑一遍**，所以要看的是 **N 次里的失败率**，
以及失败时的表现是"抛异常"还是"静默给出错误内容"。

★ 这一条直接决定 `09 §5.2` 的结论是否成立 —— 那里定的是"不自研四层防御，用官方转换器"。
若官方转换器在小模型上失败率偏高，那么**降级策略**（失败就退回原始问题单路，
`ROADMAP` 第 12 周）就不是可选项，而是常态路径。

**怎么测**：同一个抽取任务连续调用 N 次（N ≥ 20），统计失败率与失败形态。

**已经验掉的部分**：**解析链路是通的**。桩服务按 schema 生成合法 JSON，
`.entity(record)` 能正确解析出 `Extraction[title=stub, keywords=[stub-a, stub-b]]` ——
包括**嵌套的数组字段**。（搭这条链路时发现并修掉了一个真 bug：按 schema 反推键名时，
简单正则只能匹配最内层对象，会把嵌套的 `items` 误当成顶层键 —— 这类错误正是
"结构化输出必须有断言、不能看着像 JSON 就算过"的理由。）

**结果**：⏳ 待填（失败率必须来自真模型）

| 模型 | 成功/N | 失败率 | 主要失败形态 | 备注 |
|---|---|---|---|---|
| | | | | |
