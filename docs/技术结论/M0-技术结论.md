## 结论一：各模型的「思考模式」三态取值

**问题**：计划支持的每个模型，分别属于哪一态？

**口径来自冻结契约**（`frontend/src/api/models.ts:6-9`）：

```ts
/** 模型能力三态，决定界面开关如何呈现（思考模式） */
export type ThinkingMode = 'NONE' | 'TOGGLEABLE' | 'ALWAYS_ON'
```

| 取值 | 含义 | 界面行为 |
|---|---|---|
| `NONE` | 不支持思考 | 开关不出现 |
| `TOGGLEABLE` | 可开关 | 开关可切换 |
| `ALWAYS_ON` | 始终思考，关不掉 | 显示"始终开启"，置灰不可切 |

★ 契约还要求标注这个值是**「探测」还是「手工声明」**（`models.ts:48` 的
`ModelCapability.source`）—— 遇到探测不准的模型，界面要允许人工覆盖，
且**必须看得出哪个是人工填的**。这条约束会影响 `modelcatalog` 的数据形状（`source` 要落库）。

**怎么测**：对每个模型问同一个**需要推理**的问题，两次 ——
① 不传任何思考参数；② 显式要求关闭思考。对比两次响应里"思考痕迹"的有无。
探针用**原始 HTTP**取完整响应（思考内容通常走 `reasoning_content` 这类独立字段，
只看 `content` 会把"模型在思考"误判成"没思考"）。

**判据**：

| 观察 | 判定 |
|---|---|
| 两次都没有思考痕迹 | `NONE` |
| ① 有、② 没有 | `TOGGLEABLE` |
| 两次都有 | `ALWAYS_ON`（★ 但**必须先排除"是我们没传成功"** —— 见结论二，而框架侧已证会下发） |

**结果**：⏳ 待填（由探针输出）

| 模型 | 判定 | 证据（首次是否含思考 / 关思考后是否消失） | 备注 |
|---|---|---|---|
| | | | |

## 结论二：Spring AI 能否下发「思考开关」

**问题**：Spring AI 2.0.1 的 `OpenAiChatOptions.reasoningEffort(...)` 能否把开关**真的送到上游**？

**为什么这条最容易出错**：结论一的 `TOGGLEABLE` 与 `ALWAYS_ON` 之分，
**依赖"我们能成功关掉思考"这个前提**。如果框架根本没把参数发出去，那么所有模型都会被误判成
`ALWAYS_ON` —— 这个错误一路传到界面，表现是"这个模型的思考开关点了没反应"，
而排查时会先怀疑模型，**方向就错了**。

### 结果：两侧分开记

| 侧 | 结论 | 证据 |
|---|---|---|
| **框架侧** | ✅ **会下发** | ★ 实测（`OpenAiStubContractTest`，桩服务侧记录请求体）：给出 `reasoningEffort` 后，请求体里**出现** `reasoning_effort`；不给时不出现。两个方向都验了，所以不是"碰巧总有" |
| **上游侧** | ⏳ **待真模型** | 桩服务"接受"这个字段是我自己写的，**不构成证据**。需要真 Ollama 来判断它在 OpenAI 兼容端点上认不认 `reasoning_effort` |

**判据与后果**（框架侧已确定，只剩上游侧）：

| 框架侧 | 上游侧 | 结论 | 我们要做什么 |
|---|---|---|---|
| ✅ 会下发 | 接受 | ★ 最好 | 直接用，零自研 |
| — | **不认这个字段** | 上游问题 | 改用 Ollama **原生** `/api/chat` 的 `think` 参数 —— 会改端口实现，但不影响业务代码 |

> ★ 顺带被这次实测**确认**的一件事：`application.yml` 把
> `base-url` 写成 `http://localhost:11434/v1` 是**对的**。
> 证据：桩服务记录到的真实请求路径是 `/v1/chat/completions`，**不是** `/v1/v1/chat/completions`。
> 这条以前是"照着 Ollama 文档推的"，现在是实测值。

## 结论三：能否稳定产出结构化输出

**问题**：`ChatClient...call().entity(SomeRecord.class)` 在同一个小模型上连续调用，能否**稳定**返回合法 JSON？

**为什么不是"能不能返回 JSON"**：单次成功没有意义。我们的用法（查询改写、子问题分解、
行级陈述化的 LLM 变体）是**每个请求都跑一遍**，所以要看的是 **N 次里的失败率**，
以及失败时的表现是"抛异常"还是"静默给出错误内容"。

★ 这一条直接决定 `09 §5.2` 的结论是否成立 —— 那里定的是"不自研四层防御，用官方转换器"。
若官方转换器在小模型上失败率偏高，那么**降级策略**（失败就退回原始问题单路，
`ROADMAP` 第 12 周）就不是可选项，而是常态路径。

**怎么测**：同一个抽取任务连续调用 N 次（N ≥ 20），统计失败率与失败形态。

**已经验掉的部分**：**解析链路是通的**。桩服务按 schema 生成合法 JSON，
`.entity(record)` 能正确解析出 `Extraction[title=stub, keywords=[stub-a, stub-b]]` ——
包括**嵌套的数组字段**。（搭这条链路时发现并修掉了一个真 bug：按 schema 反推键名时，
简单正则只能匹配最内层对象，会把嵌套的 `items` 误当成顶层键 —— 这类错误正是
"结构化输出必须有断言、不能看着像 JSON 就算过"的理由。）

**结果**：已实测（2026-11-04，真模型直连 ollama `POST /v1/chat/completions`，**生产同构的提示词与解析**）

★ **口径（引用本表必读）**：
- **schema = 生产在用的 `HopDecision.Payload`**（`record Payload(Boolean sufficient, String nextQuery)`，
  多跳判定），**不是**上文设想的 `Extraction[title, keywords]` 形状 —— 第 14 周起生产链路真实依赖的
  就是这个形状（`MultiHopService.decide` → `ChatPort.completeAs`），测别的形状对 `09 §5.2` 没有意义。
- **提示词同构**：`MultiHopService.prompt()` 逐字（判断标准 1–4 + 用户问题 + 「已有结果（标题：正文前 100 字）」）
  + `FORMAT_SEPARATOR = "\n\n"` + `BeanOutputConverter.getFormat()` 逐字（含 schema）；
  请求体仅 `model` + `messages`（同 `UpstreamGateway`，**不带 temperature/max_tokens**）。
- **成功 = 生产可用**：`convert` 不抛 **且 `sufficient` 非 null** —— `HopDecision.from` 口径：
  解析成功但 `sufficient` 缺失/改名 ⇒ 生产照样记 D1。只看"像不像 JSON"会漏掉这一类。
- **测试路径与生产的差异**：未过真后端 `ChatPort.completeAs`（agent 不自起服务）——HTTP 直连 ollama，
  解析层为 Python 复刻 `BeanOutputConverter` 的默认 cleaner 链（Whitespace→ThinkingTag→
  MarkdownCodeBlock→Whitespace）+ Jackson 语义（未知字段忽略、缺字段→null、Boolean 宽松 coercion），
  已用真实 `spring-ai-model-2.0.1.jar` 的 20 样例行为矩阵逐条校准。
- HTTP 超时放宽 180s（本机 CPU 小模型慢，5s 会把"慢"误记成"格式失败"）；**超生产 5s 预算的比例另列**
  （超时在生产同样落 `JUDGE_FAILED`，但形态是"慢"，不混进格式失败率）。
- 采样：8 组真实形状输入（够答 / 线索要再查 / 不够且想不出 / 只答一半）× 3 次 = **N = 24 / 模型**。
- 工具：`backend/tools/check_structured_output.py`（逐条原始响应存 JSONL 取证，不入库）。

| 模型 | 成功/N | 失败率 | 主要失败形态（逐字响应片段） | 备注 |
|---|---|---|---|---|
| `qwen2.5:1.5b`（非思考） | 24/24 | **0%** | 无失败；` ```json\n{…}\n``` ` 围栏 24/24 出现、24/24 被官方清洗器救活 | 超 5s 预算 4/24（17%）；**首轮另有 1/24 失败**（粘连围栏，逐字见下表）⇒ 两轮合计 47/48（★ 取证瑕疵：首轮原始 JSONL 与汇总被第二轮同名覆盖，该条逐字片段仅存于下表） |
| `qwen3:4b`（思考可关，默认档） | 24/24 | **0%** | 无失败；围栏 24/24 全救活 | 超 5s 预算 3/24（12%）；`reasoning_content` **0/24** —— 默认档未产生思考流，"思考与 JSON 混排"风险在这一档未现身 |
| `deepseek-r1:1.5b`（思考不可关） | **未取到（0/0）** | 未取到 | 未取到 | 原因：模型已拉取入库（`ollama list` 可见），但 24 次读数任务在跨会话中断时被杀、原始记录未落盘（脚本尾部一次性写 JSONL）；按收口要求**未补跑**。可重跑：`--models deepseek-r1:1.5b --repeats 3 --via exec`（N=24，预计 15–30 分钟） |

**失败形态归类与逐字取证**（判定顺序固定：截断 > 前后废话 > markdown 围栏 > 字段缺失/改名 > 非 JSON；
前两类可靠提示词/清洗压制，**后三类只能降级**——所以归类比失败率本身更重要）：

| 形态 | 逐字响应片段 | 生产后果 | 处置 |
|---|---|---|---|
| markdown 围栏（畸形） | ```` ```{"nextQuery" : "重新查询具体版次和价格信息", "sufficient" : false}``` ```` （真模型，`qwen2.5:1.5b` 首轮 c3：围栏与 JSON **粘连无换行**，`MarkdownCodeBlockCleaner` 按"首行=围栏标记"切，把 `{` 一并切掉） | `convert` 抛 ⇒ D1 | 提示词可压：常规 ` ```json\n{…}\n``` ` 形状实测 48/48 全被救活，**畸形围栏才是失败源** |
| 前后有废话 | `好的，我判断如下：\n```json\n{…}\n```\n希望对你有帮助`（合成探针；deepseek 组未取到，真模型"前后废话"形态未补到样本） | `convert` 抛 `Unrecognized token '好的'` ⇒ D1 | **只能降级或补"宽松层"**：官方转换器**不**取第一个完整 JSON 对象（`StructuredOutputConverterTest.proseAroundJsonIsNotTolerated` 已实测） |
| 字段缺失或改名 | `{"nextQuery": "再查一下…"}`（缺 `sufficient`）／ `{"next_query": …}`（改名） | `convert` **不抛**，但 `sufficient=null` ⇒ `HopDecision.from` 判失败 ⇒ D1 | **只能降级**；★ 改名连报错都没有（宽松匹配静默按缺省处理）——"解析成功"≠"判定可用"的实证 |
| 截断 | `{"sufficient": false, "nextQu`（合成探针） | `convert` 抛 `Unexpected end-of-input` ⇒ D1 | 降级（受 max_tokens/预算限制） |
| 非 JSON | `我不知道怎么回答这个问题`（合成探针） | `convert` 抛 `Unrecognized token` ⇒ D1 | 降级 |

### 附：`HopStop.JUDGE_FAILED` 发生率断言设计（下一版怎么做，本轮只给设计不实现）

**为什么格式失败率低仍要这条断言**：`JUDGE_FAILED` 是**同一个出口的多来源事件** ——
解析异常只是来源之一，**超生产 5s 预算**同样落 D1（`MultiHopService.decide` catch `BusinessException`，
而 `completeAs` 的 timeout 就是 `DEFAULT_BUDGET_MS = 5_000`）。本次实测超 5s 的比例：
`qwen2.5:1.5b` 4/24（17%）、`qwen3:4b` 3/24（12%）—— **格式读数绿 ≠ `JUDGE_FAILED` 率低**。

**设计两条（下一版做）**：
1. **发生率断言**：端到端真模型跑 N 次多跳问答（N ≥ 100），断言 `JUDGE_FAILED 次数 / N < 上限`
   （首版建议上限 10% 作观察值，写进 `10 §6.3` 的 D1 计数口径旁，随读数修订）。
   ★ 断言必须**能红**：故意注入畸形响应或把 timeout 调到 1ms ⇒ 断言要报红（反证），
   否则它只是又一条常绿的假闸门。
2. **形态归因拆列**：`JUDGE_FAILED` 计数至少拆三列 —— **格式失败 / 超预算 / 判定缺字段（sufficient=null）**；
   三者处置完全不同（改提示词与清洗 / 改预算或降级 / 改 schema 约束），混在一个计数里无法行动。
   归因判定顺序可直接复用 `backend/tools/check_structured_output.py` 的 `classify_failure`
   （截断 > 前后废话 > markdown 围栏 > 字段缺失/改名 > 非 JSON）。
