## 一、复现的硬性障碍（务必先解决）

### 障碍 1 · 15 张业务表的建表脚本缺失 【已核实】

**现象**：交付包中的 `deploy/sql/schema.sql` 是**增量脚本**（以 `ALTER TABLE` 为主）。后端共定义 25 张业务表（由实体映射逐一核对），其中**只有 10 张**在建库脚本中带 `CREATE TABLE`，**另 15 张完全没有任何建表语句**。

**有建表语句的 10 张**：`qa_knowledge_process`、`qa_ai_model`、`qa_role_type`、`qa_question`、`qa_question_segment`、`qa_crawl_spider_conf`、`qa_crawl_job`、`qa_crawl_proxy`、`qa_application_type`、`qa_metric_config`、`qa_generate_record`

**缺失建表语句的 15 张**（★ 为核心主链路）：

| 表 | 业务含义 | 影响 |
|---|---|---|
| ★ `qa_knowledge_base` | 知识库 | 核心，无表则知识库功能全废 |
| ★ `qa_knowledge_type` | 知识库分类 | 分类树不可用 |
| ★ `qa_history_session` | 会话 | 核心，无表则无法提问 |
| ★ `qa_history_msg` | 消息 | 核心，无表则无法保存问答 |
| ★ `qa_application_info` | 应用/智能体 | 核心，无表则无法建应用 |
| ★ `qa_assistant_role` | 角色词 | 提示词角色不可用 |
| `qa_api_key` | 应用 API 密钥 | 开放接口不可用 |
| `qa_base_model` | 基础模型库 | 模型管理无法选基础模型 |
| `qa_ppt_template` | PPT 模板 | PPT 生成不可用 |
| `qa_share_msg` | 分享消息 | 分享功能不可用 |
| `qa_token_key` | 公开访问凭证 | 公开链接/嵌入不可用 |
| `qa_user_feedback` | 用户反馈 | 反馈与满意度不可用 |
| `qa_white_list_url` | 来源白名单 | 访问限制不可用 |
| `vector_store_content` | 分段/切片 | 核心，无表则分段治理不可用 |
| `vector_store_embedding` | 向量化记录 | 向量化状态不可追溯 |

**后果**：在**全新数据库**上执行建库步骤，会在 `alter table qa_knowledge_base ...` 处报错中断，后续脚本不再执行，业务表大面积缺失，系统无法使用。

**复现做法**：
1. 从已运行的现有环境导出这 15 张表的结构，补入初始化脚本：
   ```bash
   pg_dump --schema-only -t 'qa_*' -t 'vector_store_*' -h <host> -U <user> -d <db> > 01_business_tables.sql
   ```
2. 若无法访问现有环境，则依据后端实体类（`blade-service-api` 下的 25 个 `*Entity.java`，含 `@TableName` 注解）反向编写 DDL，**字段名与类型必须与实体逐一核对**；
3. 补齐后必须验证：知识库、应用、会话、分段四条链路均可读写。

> 该项**不影响**演示环境（演示库是预置好的），只影响"从零重建"。若交付目标包含"新环境部署"，这是必须先补的第一件事。
>
> 另注：Spring AI 的向量主表（`vector_store`）**不在此列**——它由框架在运行时按配置的维度自动创建，无需手工建表。

### 障碍 2 · 业务菜单树未随 SQL 交付 【已核实】

**现象**：交付的菜单脚本只有两份，且都只包含一个小模块：

| 文件 | 内容 |
|---|---|
| `question.menu.sql` | 问题管理（1 个菜单 + 4 个按钮） |
| `roletype.menu.sql` | 角色类别（1 个菜单 + 4 个按钮） |

而基础 SQL 中的 169 条菜单记录**全部是平台基座菜单**（工作台/系统管理/监控/流程/资源/报表/任务等），**不含任何 AI 业务菜单**（智能问答、知识库、应用、模型管理、爬虫、看板等）。

**后果**：即使数据库建好、账号建好、页面文件齐全，用户登录后**左侧导航里也没有 AI 业务入口**——因为菜单表和按钮权限表里没有对应记录。

**复现做法**：
1. 在菜单管理中**手工建立**业务菜单树（推荐做法：从现有环境导出 `blade_menu` 中业务相关的记录）；
2. 菜单路径必须与实际页面文件位置严格对应，否则点击白屏；
3. 每个页面的操作按钮也需作为 `category=2` 的按钮记录建入，否则页面内所有按钮都不显示（会被权限判定为未授权）；
4. 建完菜单后需分配给角色并**重新登录**才生效。

> **这是复现工作量最大、最容易卡住的一环。** 建议在复现启动前，先从现有环境执行一次 `blade_menu` 全量导出作为基线。

### 障碍 3 · 业务字典数据不完整 【推断】

**现象**：已知随 SQL 交付的字典只有 `knowledge_domain`（知识领域）与 `ImportFileType`（导入文档类型）两组。而以下字典被前端大量引用：

| 字典编码 | 用途 | 缺失后果 |
|---|---|---|
| `application_type` | 应用分类 | 建应用时分类下拉为空 |
| `apply_type` | 应用类型 | 同上 |
| `knowledge_type` | 知识库类型 | 建知识库时分类下拉为空 |
| `model_type` | 模型类型 | 建模型时用途下拉为空 |
| `supplier` | 模型供应商 | 模型管理无法筛选、无法新增 |
| `ppt_type` | PPT 模板类型 | PPT 模板分类为空 |
| `no_seg_refer` | 分段引用设置 | 检索参数配置异常 |

**复现做法**：从现有环境导出 `blade_dict_biz` 全表，或依据业务口径补齐上述字典项。

### 障碍 4 · 系统参数缺失 【推断】

以下参数被功能直接依赖，缺失会导致对应功能不可用或报错：

| 参数 | 用途 |
|---|---|
| `account.initPassword` | 新用户初始密码 |
| `tenant.default.password` | 租户管理员默认密码 |
| `crawl.operationManual.download` | 爬虫操作手册下载地址 |
| `apikey.document.download` | API 接口文档下载地址 |

**复现做法**：导出 `blade_param` 或在参数管理中补齐。

## 五、环境与配置的硬性约束

这些约束不是缺陷，而是**复现时必须遵守的前提**：

| 编号 | 约束 | 说明 |
|---|---|---|
| ENV-01 | 至少 2 个模型**不可删除** | 有模型名被后端代码硬编码引用（知识图谱抽取/消歧场景）。删除后相关功能报"模型不存在" |
| ENV-02 | 向量模型**不可更换** | 向量维度固定为 768，向量表按此维度创建。更换需删表重建并**重灌全部知识库** |
| ENV-03 | 向量模型上下文仅约 1K token | 分段过长会被截断，分段长度需小于该上限 |
| ENV-04 | 问答接口需放宽长连接超时 | 需约 600 秒，否则长回答被截断 |
| ENV-05 | 请求体加密默认关闭 | 加密密钥在代码中为占位值，实际未启用；如需启用须配置真实密钥 |
| ENV-06 | 免登录场景租户标识被固定 | 公开链接与嵌入浮窗固定使用默认租户，多租户下须评估内容暴露风险 |
| ENV-07 | 两套后台共用账号体系 | 靠客户端标识区分菜单，客户端配置丢失会导致"登录后无菜单" |
| ENV-08 | 从源码重建需商业基座私有构件 | 私有构件不在公共仓库，交付包中已附带离线构件包，重建时需先安装 |

## 八、结语：复现难度评估

| 环节 | 难度 | 主要风险 |
|---|---|---|
| 环境部署 | 中 | 组件多（约 32 个容器），资源要求高（内存 ≥24GB） |
| 数据补齐 | **高** | 核心表 DDL 与业务菜单树均缺失，需从现有环境导出 |
| 前端运行 | 低 | 构建产物随包提供，开箱可用 |
