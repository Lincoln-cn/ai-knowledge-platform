# 测试语料（`corpus/`）

> ★ **这个目录里，只有 `README.md` 和 `qa.sample.jsonl` 进 git。** 其余一律不进。
> 规则在根 `.gitignore` 的「**第一道防线**」一节 —— 理由见下。

---

## 一、这是干什么用的

`ROADMAP §2.3` 的量化指标（**B1 命中率 ≥70%** · **B2 答案可用率 ≥75%** · **B3 引用准确率 ≥80%** ·
**B4 首字延迟 ≤10s**）**只能在一批真实语料上测出来**。桩（`backend/tools/openai_stub.py`）的语义是随机的，
它能证明"链路通了"，但**读不出"答得对不对"**。

`ROADMAP §6.1` 对这批东西的要求（原文口径）：

- **P1 测试语料 ≥50 份真实业务文档**（≥200 万字，覆盖 **PDF / Word / Markdown**）
- **问题集 ≥50 个真实问题**（**每个标注期望命中**）
- **≥2 名评审人**（B2「答案可用率」是人工判定，不是自动判定）

⇒ 本目录就是放这些**输入**的地方。

## 二、为什么放在仓库根，而不是 `backend/src/test/resources/`

本仓已经有一个"被提交的测试文档"的落点：`backend/src/test/resources/fixtures/`
（例如 `structured.docx`，被 `frontend/check_classification_e2e.py:45` 引用）。

**真实语料不放那里**，两条理由：

1. `src/test/resources/` 的语义是「**随测试一起打包进 classpath 的小夹具**」。
   50 份文档 ≥200 万字不是夹具，会被打进产物、拖慢构建；
2. ★ 更重要的：那个目录里的东西**默认是要提交的**。而语料**默认是不提交的**。
   把两类东西放一起，迟早会有人 `git add` 顺手带进去。

放仓库根、并与 `.ollama-data/`（几 GB 模型数据，同样被忽略）同族的理由：
**它们是"本机运行需要的资产"，不是"仓库的资产"**。

## 三、目录结构

```
corpus/
├── README.md            ← 提交（本文件）
├── qa.sample.jsonl      ← 提交（示例，**它就是格式规范**）
├── documents/           ← 不提交（真实文档：.pdf / .docx / .md）
└── qa.jsonl             ← 不提交（真实问题集，从 qa.sample.jsonl 复制改名后填写）
```

初始化（内容不进 git，所以目录要自己建）：

```bash
mkdir -p corpus/documents
cp corpus/qa.sample.jsonl corpus/qa.jsonl
# 然后把真实文档放进 corpus/documents/，把真实问题填进 corpus/qa.jsonl
```

> ★ 文件名 `qa.jsonl` 与示例 `qa.sample.jsonl` 的差别只有 `.sample` 一词 ——
> 不是巧合：**示例可以直接复制成真文件**，省掉"该叫什么名字"的猜测。

## 四、`qa.jsonl` 的格式（**以 `qa.sample.jsonl` 为准**）

一行一个 JSON 对象（JSONL）：便于追加、diff 干净、不会因为少一个逗号整份坏掉。

| 字段 | 必填 | 含义 |
|---|---|---|
| `id` | ✅ | 唯一标识，形如 `q-001`（★ 别用行号当 id —— 中间插一条就全错位） |
| `question` | ✅ | 真实用户会怎么问（★ 用**业务原话**，不要改写成书面语：B1 测的是"用户这么问能不能命中"） |
| `expected_document` | ✅ | 期望命中的文件名，**必须与 `corpus/documents/` 下的实际文件名逐字一致** |
| `expected_snippet` | ✅ | 期望**出现在引用原文里**的片段 → 这是 **B3 引用准确率**的判据 |
| `expected_topic` | ⭕ | 一两句语义线索，用于 **B1 命中率**的粗判与人工复核 |
| `notes` | ⭕ | 备注（谁标的、为什么这么标、有争议时记在这里） |

★ **`expected_snippet` 必须是文档里逐字存在的片段**（去空白后比对），不是改写过的概括 ——
否则 B3 会把"引用正确"判成"引用错误"，而这个错误**看起来像产品缺陷**。

## 五、★ 隐私与体积纪律

1. **真实语料不进 git，也不进 issue / PR / 聊天记录**。要引用某段内容说明问题，用
   "文档 X 第 N 节，含某类信息"这种描述，不要贴原文；
2. 若文档本身含个人信息（人名 / 证件号 / 手机号 / 车牌等），**先用脱敏副本**，
   且脱敏副本同样不进 git；
3. 本目录被忽略**不是"临时方案"** —— 它就该长期如此。想改这条规则，先回答：
   "这批文档的版权与密级，允许它出现在公开仓库里吗？"

## 六、语料缺失时，闸门必须**显式**说"没有语料"

★ 这一条是给写 B1–B7 闸门的人看的：
**没有语料时，闸门必须打印"缺少语料"并以非 0 退出（或明确的 SKIP），绝不许静默通过。**

理由：B1–B7 是本项目的**验收指标**。一个"没语料也绿"的闸门，会让验收报告里出现
**凭空的达标结论** —— 那比"没有读数"严重得多（本仓头号病 `silent-failure` 的形态）。

## 七、合成语料（`corpus/synthetic/`）—— **不是** P1 语料

真实 P1 语料要人工收集与标注（还需 ≥2 名评审人），在那之前，**解析 / 切分 / 向量化 /
检索这条链路可以用一批"同形状的合成语料"先跑起来**：

```
corpus/synthetic/
├── documents/           ← 70 份（.md / .docx / .pdf / .txt）
├── qa.jsonl             ← 215 条标注问题
├── manifest.json        ← 每份文档的 sha256 / 字数 / 段落锚点
└── README.md            ← 生成器写的目录说明
```

生成与校验（都确定性、可重跑）：

```bash
python tools/gen_corpus.py            # 生成 70 份（md 50 / docx 8 / pdf 8 / txt 4），约 2.1M 字
python tools/gen_corpus.py --docs 3   # 冒烟：只生成前 3 份
python tools/check_corpus.py          # 离线校验（文档数 / 总字数 / 四格式 / snippet 逐字且全语料唯一）
python scripts/parse_corpus.py --corpus corpus/synthetic   # 上传 → 解析 → 向量化 → 问答核对
```

### 7.1 它能证明什么

- **四种格式的解析链路都通**（PDF 文本层、DOCX、Markdown、TXT），且每份都解析出正文；
- **入库吞吐与耗时**（70 份 / 200 万字量级，可读单份与整批的时间）；
- **文档列表分页**：超过后端单页上限（100）时的行为 —— 这条以前写死 `size=50`，**70 份会静默只看前 50 份**；
- **B3 的判据本身可用**：`expected_snippet` 是"去空白后逐字存在"的，能验证比对口径实现对了。

### 7.2 ★ 它**不能**证明什么（写读数时必须一起写）

| 指标 | 为什么不能用合成语料读 |
|---|---|
| **B1 命中率** | 问题与文档由同一套模板生成，措辞高度雷同 ⇒ 命中率**虚高**，与真实用户提问的分布无关 |
| **B2 答案可用率** | 需要**业务评审人**判定"答案能不能用"，合成语料没有业务语境，评不出 |
| **B3 引用准确率** | 能验"比对口径实现对了"，但引用是否**该**引那一段，要真实语料 |
| **检索质量/召回** | 合成文档是模板拼接、句间无真实逻辑依赖，测不出"跨段落推理"这类真问题 |

⇒ 用合成语料跑出来的任何数字，**必须标注为「合成语料读数」**，不许写进验收台账当 B1–B7 的结论。
`manifest.json` 里已写死 `"kind": "synthetic"` / `"is_p1_corpus": false`，`tools/check_corpus.py`
会核这两个字段 —— 就是为了防止某天它被当成 P1 语料。

### 7.3 已知的可接受缺陷

模板句池有限（合同 8–10 句/类、纪要 9 句/类），同一份文档内仍会出现"同一模板换数字"的近似重复。
这对"链路通不通"没有影响，但对"答得好不好"有影响 —— 正是它不能读 B2 的原因之一。
